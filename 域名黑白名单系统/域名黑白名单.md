# 域名黑白名单系统

## 介绍一下这个系统

我负责了域名黑白名单核心模块设计：

- 白名单：支持国家管控域名、拍卖的域名、或大客户特权注册、域名秒杀抢注、热门域名等等
- 黑名单：拦截恶意注册、SQL 注入及恶意高频攻击 IP

用的是三级缓存、分别是 Redis、本地缓存和 MQ

## 为什么用 Redis

- 峰值 QPS 流量压力下、采用三重存储结构、两级缓存架构来进行设计
- 峰值假如按照 1 万的量去估、1 万量全都打到 DB 上、DB 应该可以顶得住、但还是会引入分布式缓存 Redis、因为 Redis 快、引入这个是非常常见的
- 三重存储就是本地缓存、分布式缓存、还有 DB

## 介绍一下多级缓存

我们项目里是三级缓存：

- **第一层本地缓存**：主要拦截热点请求、减少对 Redis 的冲击、解决 hot key 和突发流量问题
- **第二层 Redis**：作为分布式共享缓存、承接大部分读请求
- **第三层 MySQL/DB**：作为最终的数据源

整体上是本地缓存 + Redis + DB 的三级结构、主要目标是提升性能、降低延迟和保护数据库。

## 为什么要引入本地缓存？本地缓存的作用是什么

### 面试回答版

我们本地缓存存的是黑白名单查询结果和部分只读规则结果、key 不只有域名维度、也有 IP 维度和组合规则维度、比如 `whitelist:domain:{domain}`、`blacklist:ip:{ip}` 这种。

value 主要是某个域名或 IP 是否命中黑白名单、命中规则后的标志位和少量基础信息。

### 问题背景

我们之所以在黑白名单系统里引入本地缓存、主要是为了解决 **Redis 热 Key 问题**。

在域名业务中、存在非常典型的热点访问场景、关键词是**流量突发性**：

- 秒杀类的热门域名「8888.com」、活动一开始、成千上万的请求会同时去查询它的状态
- 恶意 IP 在短时间内疯狂刷接口、这种 Key（比如 `blacklist:ip:1.2.3.4`）的访问频率会瞬间飙升

这时候如果所有请求都直接打到 Redis、就会造成**网络 IO 拥堵和热点 Key 拖垮缓存节点**的问题、反而影响了整体系统的稳定性。

### 解决方案

在 SDK 层加了一层 **Guava 本地缓存**、让热点 Key 在本机就能被快速命中、不必每次都请求 Redis。

这样一来：

- 显著降低 Redis 的压力
- 把热点访问的延迟时间降低
- 将原本集中在单一 Redis 节点上的巨大压力、**分散**到成百上千个应用服务器实例的内存中、每个实例只用处理一小部分流量、从而去解决了热 Key 的单点瓶颈问题

### 读写分离设计

本地缓存只用于读请求、不参与写操作。因为本地缓存的定位是一个读优化层、主要用来拦截热点请求、保护 Redis、而不是承担数据写入或强一致逻辑。

像域名拍卖这种场景、涉及库存扣减和购买、这类操作必须保证强一致性、一般会集中在 Redis 或数据库、通过原子操作或者事务来完成。本地缓存是多节点、短 TTL 的、如果参与写操作会带来数据不一致甚至超卖的问题。

所以在架构上是明确做了读写分离：本地缓存只负责读路径优化、写路径完全交给下游系统处理。







## 为什么设置本地缓存过期时间为 5s

我们设置本地缓存过期时间为 **5 秒**、是经过权衡后做出的选择、主要考虑四方面：

我们当时选了 **1s、3s、5s、10s** 四个梯度去压测  
 主要观测三个指标：**本地缓存命中率、堆内存占用、GC频率**。

1. **内存占用率**：本地缓存不能太大、否则堆内存占用过高、会影响服务稳定性
2. **GC 情况**：如果缓存时间过长（比如 10 秒）、缓存对象会在新生代多次 Minor GC 后晋升到老年代、占满老年代空间、触发 Full GC。Full GC 开销大、会暂停所有应用线程、对高并发服务影响严重
3. **缓存命中率**：如果缓存时间过短（比如 1 秒）、高峰期缓存可能刚写入就失效、大量请求直接打到 Redis 上、命中率低、无法有效保护 Redis、也解决不了热 Key 问题
4. **数据一致性**：缓存时间太长可能导致脏数据存在时间过久、需要结合业务需求控制

### 10s 的问题

时间太长（如 10 秒）：虽然命中率高、但会导致 JVM 内存占用过高、大量对象长期驻留在堆内、无法被及时回收、从而占满老年代空间、频繁触发 Full GC、影响服务稳定性。同时、数据一致性延迟更长。

### 1s 的问题

内存占用低、但对于持续几秒的流量高峰、缓存可能刚写入就失效了、导致大量请求击穿本地缓存、打到 Redis 上、缓存命中率不理想、没有起到很好的保护 Redis 的作用、同时没有很好的解决热 key 问题。

### 结论

压测后选择了 5s、能将内存占用稳定在可接受的范围（50%-60%）、**GC 稳定**、同时命中率也达到了很高的水平（接近 97%）

这个问题问得很好、5秒的脏数据窗口确实存在，、们当时也专门讨论过这个问题。

最终认为5秒可以接受、主要是基于两个判断：

**第一、黑名单加入本身就不是即时生效的。** 运营人员发现一个恶意IP、走审批流程、提交入库，这个链路本身就需要几秒甚至几十秒。所以系统层面多5秒、在业务上几乎感知不到

**第二、真正需要秒级封禁的场景、我们有独立的紧急通道。** 比如正在进行的DDoS攻击、这类情况不走常规MQ链路、而是直接操作Redis做实时封禁、绕过本地缓存的TTL窗口。本地缓存针对的是查询热点优化、不是紧急封禁的执行路径

所以5秒这个值、是在压测数据（命中率97%、内存稳定在50-60%）的基础上

 结合业务上普通封禁不需要毫秒级生效这个判断、权衡后选的

结论大概是这样：

- **1s**：命中率很低，只有60%左右、高峰期缓存刚写入就失效、大量请求还是打到Redis上，基本没起到保护作用
- **3s**：命中率提升到了85%左右、内存和GC都还好、但命中率还不够理想、热点流量还是有一部分在穿透
- **5s**：命中率接近97%、内存稳定在50%-60%、GC频率正常、没有出现对象大量晋升老年代的情况
- **10s**：命中率和5s差不多、提升不明显、但内存占用明显上去了、而且开始观察到Minor GC后对象晋升老年代的情况，Full GC风险变高

所以5s是一个**命中率收益最大、内存和GC代价可控**的拐点、往上收益边际递减、往下保护效果不够、最终就定在了5s









## 本地缓存的 key 和 value 是什么

本地缓存存的主要是黑白名单查询结果和域名访问相关的只读数据。

**key 不只域名维度、也包括 IP 维度和部分组合规则维度**：

- `whitelist:domain:{domain}`
- `blacklist:domain:{domain}`
- `blacklist:ip:{ip}`
- `rule:{domain}:{ip}` 组合维度结果

**value 一般不是特别复杂**、核心是某个对象是否命中黑名单/白名单、命中的规则结果、以及对应的一些基础信息或标志位。它们都属于读多写少、允许短时间不一致的数据。

域名本身量确实不大、稳定在几千/几万级、单纯域名缓存占用很小。真正容易把缓存规模和对象 churn 拉起来的是 IP 这种高基数 key——在恶意刷接口场景下、不同 IP 的数量可能在短时间内快速膨胀。

本地缓存的价值不只是省 Redis、而是吸收尖刺流量。

## 为什么会出现 Redis 热 key 的问题、热 key 是什么、会带来什么问题

热 Key 指的是在 Redis 中短时间内**极高频访问的某个 Key**、比如 QPS 里 80% 都打在这个 Key 上。

### 为什么会出现热 Key？

本质原因是**访问分布不均（数据倾斜）**、典型场景有：

- 业务热点：秒杀商品或热门数据、大量请求集中访问同一个 Key
- 缓存设计不合理：黑白名单或配置数据全部放在一个 Key
- 缓存粒度过粗：导致所有请求打在同一个 Key
- 突发流量或攻击导致某个 Key 被打爆

### 会带来什么问题？

大量请求打到同一个 key 会导致 Redis 的单点 QPS 飙升、甚至成为瓶颈。还可能带来缓存击穿、穿透等问题。以及系统负载不均衡、请求会集中到某一个节点、导致这个节点过载、而其他的节点会比较空闲。

分散 key 的情况下、请求会在多个 key、多个节点之间分摊、系统是水平扩展的。而热 key 场景下、本质是所有请求集中到单个 key、对应单个节点、形成单点瓶颈、无法利用集群能力

## 假如说十万个请求打到分散的 key 和十万个请求打到同一个 key 有什么区别

这两种情况**本质区别很大**：

- **分散的 key**：10 万请求打到 10 万个不同的 Key、流量是分散的、请求会均匀分布在不同 Key 上、Redis 可以并发处理、整体压力是可控的
- **同一个 key（热 Key）**：10 万请求打到同一个 Key、所有请求都会集中到同一个数据上、虽然 Redis 是单线程处理命令、但这个 Key 会成为热点、导致 CPU、网络、带宽都集中在这里、容易成为单点的瓶颈

## Redis 明明能扛 10 万 QPS、为什么还要本地缓存

不是 Redis 理论 QPS 不够、而是**热点 key、突发流量、长尾 RT 和链路隔离**问题、让单用 Redis 不够稳。

**Redis 平均抗 10 万 QPS、这是一个比较理想化的整体吞吐指标、但实际业务里不能只看总 QPS、还要看访问分布是否均匀。**

- 我们的问题不是所有 key 都平均访问、而是存在明显的热点 key 和流量尖刺
- 某个热点名单或者热点规则结果、可能在短时间内被大量重复访问、这会导致单 key 访问集中、Redis RT 出现长尾、进而阻塞其他正常请求
- 如果热点 key 对应的数据对象本身比较大、还会叠加大 key 带来的网络传输和反序列化开销、形成连锁放大

所以即使 Redis 总体 QPS 还没打满、我们也可能已经在热点 key 上看到明显瓶颈了。引入本地缓存、目的不是替代 Redis、而是把热点读流量分摊到各个应用实例内存里、进一步降低 Redis 压力和长尾

## 为什么要用 Guava Cache、有没有调研过其他

当时选 Guava 主要是因为它接入成本低、API 简单、在我们当前场景下功能够用、像 TTL、容量控制这些都能满足。

 如果进一步追求更高命中率和更好的淘汰策略、Caffeine 会更好、因为它在并发性能、命中率和淘汰算法上通常更优。 

但当时我们的目标是快速解决热点 key 和突发流量问题、所以优先选择了团队更熟悉、落地更快的方案

## 本地缓存会不会影响一致性

会有短时间不一致、但因为 TTL 很短（比如 5 秒）、而且它不参与写路径、所以不会影响核心交易逻辑、只影响查询结果的实时性。

## 如何保证一致性

**三重方案**：更新 DB 时发消息到 MQ 异步更新 Redis、监听 DB 的 `binlog` 进行增量对账修复、以天为维度定时全量扫描数据与 Redis 对比修复。

### 第一层：通过 MQ 消息队列实现准实时同步

在核心业务流程中、当运营人员通过后台（数据库）更新黑名单状态时、采用写 DB 后立即发送 MQ 的异步化方案。更新完数据库之后、立刻向消息队列发送一条变更通知、独立**缓存同步服务**订阅这个 MQ 主题、收到变更消息后立即去更新 **Redis 缓存**。

最大好处是**主业务流程和缓存更新完全解耦**、保证了 API 接口的低延迟和高吞吐量。同时利用 MQ 本身具备的**持久化和失败重试**机制、确保了缓存更新的通知能够可靠送达。

### 第二层：通过监听数据库 Binlog 进行增量校对

为了防止第一层出现代码 Bug 或消息丢失等极端情况、部署了一套独立的对账系统。核心原理是**订阅并解析数据库的 Binlog 日志**——会记录所有的数据变更。一旦监听到数据变更、立刻主动与 Redis 中的数据进行比对、如果发现数据不一致、**强制以数据库为准进行修复**。

这一层确保了任何来源的数据库变更都能被检测和修复、是保证数据准确性的第二层。

### 第三层：通过每日全量任务作为最终兜底

有一个定时任务、以天为维度定时全量扫描数据与 Redis 对比修复。在每天凌晨的业务低峰期、**扫描前一天发生变更的所有数据**、进行一次**全量的 DB-Redis 数据比对**。

这个过程不仅能修复前两层可能遗漏的任何细微差错。如果修复任务连续失败并达到设定的阈值、就会触发高级别告警、通知人工介入。这套机制确保了系统具备自我审计和异常发现的能力、保证了数据 100% 可靠。

## 多个请求同时到 Redis 时、本地缓存怎么更新（本地缓存失效风暴）

用的是旁路缓存（**Cache Aside**）。

**读：** `先查缓存 → miss → 查 DB → 回填缓存`

**写：** `更新 DB → 删除缓存`

### 问题本质

本地缓存过期后、大量请求同时发现本地缓存没命中、都去打 Redis、那么谁来回填本地缓存？会不会很多请求一起回填、造成击穿/抖动？

Redis 怎么更新到本地缓存并不是 Redis 主动推给本地缓存、而是**应用在访问 Redis 后、把结果写回本地缓存**

#### 读路径

1. 先查本地缓存
2. 本地 miss 查 Redis
3. Redis miss 再查 DB
4. 查到后回填 Redis
5. 再回填本地缓存

#### 写路径

1. 更新 DB
2. 发 MQ 通知缓存同步服务
3. 同步 Redis / 删除 Redis
4. 本地缓存依赖 TTL 自然过期，或通过消息广播失效

### 方案一：简单版

本地缓存过期后、如果多个请求同时 miss、本质上都会去访问 Redis、拿到结果后再各自尝试写回本地缓存。因为写入的是同一份值、所以即使存在短时间重复回填、问题也不大。本地缓存的核心目标是抗热点、削峰、而不是做严格的单flight 控制、所以实现上没有做复杂的并发锁、而是接受少量并发回源。

### 方案二：进阶版

为了避免本地缓存失效瞬间大量请求同时打 Redis、可以在单机内部加一个互斥控制、比如 mutex / **singleflight**。这样同一个 key 过期后、只让一个线程去 Redis 拉最新值、其他线程等待这个结果、然后共享同一次重建结果、再一起读本地缓存。

### 面试回答版

我们本地缓存不是由 Redis 主动更新的、而是在本地缓存 miss 之后、由请求线程去 Redis 读取最新值、再回填到本地缓存。更新动作是在应用侧完成的。

并发场景下、如果多个请求同时发现本地缓存过期、最简单的做法是它们都会访问 Redis、拿到结果后再写回本地缓存、因为写的是同一份数据、所以即使有少量重复回填也可以接受。

进一步优化的话、可以在单机内部对热点 key 加互斥锁或者 **singleflight**、只让一个请求去 Redis 拉数据、其他请求复用结果、避免瞬时并发击穿 Redis

## Redis 过期策略 & 突然变热的域名

我们在设计 Redis 缓存策略时、没有采用单一过期方案、而是根据数据访问特征做了区分。

### 普通数据（99%）

采用 **定期过期（24 小时 + 随机值）**：

- 作为**兜底机制**、防止 MQ 或 Binlog 更新链路出现异常导致永久脏数据
- **节省内存**、避免冷数据长期占用
- **随机 TTL** 防止大量 Key 同时失效引发缓存雪崩

当 Redis 的缓存过期时、会触发**回源机制**：如果是普通数据、就从数据库中回源、然后再写回 Redis。

### 极度热门且稳定的数据（<1%）

采用 **永不过期策略**。比如公司核心域名 `tencent.com` 的解析记录、或永久合规黑名单这类数据。它们在 Redis 里被设置的是永不过期、这类数据访问量极高、更新频率极低、而且依赖于主动更新的机制（MQ 或 Binlog 推送）、数据非常稳定且更新路径完全可控、信任主动更新机制、用永不过期换取极致性能和稳定性。

### 突然变热的场景

比如某个域名突然流量暴涨、会监控 Redis 命中率和访问量、一旦发现访问量突增、会**自动提升这类 Key 的缓存等级**、比如延长 Redis 过期时间、甚至提升为永不过期 + 主动更新、防止缓存击穿和流量抖动。

这样、本地缓存保证短时高性能、Redis 缓存保证全局一致性、两者配合可以在高并发下平滑应对热点。
