# 介绍一下多级缓存



我们项目里是三级缓存。

第一层是本地缓存、主要拦截热点请求、减少对 Redis 的冲击、解决 hot key 和突发流量问题

第二层是 Redis、作为分布式共享缓存、承接大部分读请求

第三层是 MySQL/DB、作为最终的数据源

整体上是本地缓存 + Redis + DB 的三级结构

主要目标是提升性能、降低延迟和保护数据库









# 为什么要引入本地缓存？本地缓存的作用是什么



### 一分钟面试回答版

**我们本地缓存存的是黑白名单查询结果和部分只读规则结果、key 不只有域名维度、也有 IP 维度和组合规则维度、比如 `whitelist:domain:{domain}`、`blacklist:ip:{ip}` 这种**

**value 主要是某个域名或 IP 是否命中黑白名单、命中规则后的标志位和少量基础信息**



**一开始我们其实只用了 Redis、但后来发现问题不在于 Redis 理论总 QPS 不够、而在于热点 key 和突发流量会让 Redis 出现明显的 RT 长尾。尤其是活动场景下、访问会集中打到少量 key 上、如果对象又偏大、还会叠加大 key 带来的网络传输和反序列化开销、影响其他请求。**

**所以后来在 SDK 层加了本地缓存、把热点流量分摊到各个应用实例内存里、进一步保护 Redis。**

**TTL 最后选 5 秒、也是压测后确定的折中值。**

**太短命中率不够、拦不住流量**

**太长又会增加一致性延迟和本地内存、GC 压力**

**5 秒在命中率、稳定性和一致性之间相对比较平衡**











我们之所以在黑白名单系统里引入本地缓存、主要是为了解决**Redis 热 Key 问题**。

在域名业务中、其实存在非常典型的热点访问场景、我用一个关键词描述就是它的流量突发性

比如秒杀类的热门域名「8888.com」、活动一开始、成千上万的请求会同时去查询它的状态

又或者是一个恶意 IP 在短时间内疯狂刷接口、这种 Key（比如 `blacklist:ip:1.2.3.4`）的访问频率会瞬间飙升



这时候如果所有请求都直接打到 Redis、就会造成**网络 IO 拥堵和热点 Key 拖垮缓存节点**的问题、反而影响了整体系统的稳定性



所以我们在 SDK 层又加了一层 **Guava 本地缓存、**让热点 Key 在本机就能被快速命中、不必每次都请求 Redis

这样一来、既能显著降低 Redis 的压力、也能把热点访问的延迟时间降低

我们将原本集中在单一Redis节点上的巨大压力、**分散**到了成百上千个应用服务器实例的内存中

每个实例只用处理一小部分流量、从而去解决了热 Key 的单点瓶颈问题

对你这个实习的经历还是比较感谢没有必要在你这边进行分开、你只要把搜索和注册业务分开就行了、然后搜索给他八个端口、注册给他两个端口就可以了。**数据一致性**：缓存时间太长可能导致脏数据存在时间过久、需要结合业务需求控制





我们这个本地缓存只用于读请求、不参与写操作。因为本地缓存的定位是一个读优化层、主要用来拦截热点请求、保护 Redis、而不是承担数据写入或强一致逻辑

像域名拍卖这种场景、涉及库存扣减和购买、这类操作必须保证强一致性、一般会集中在 Redis 或数据库、通过原子操作或者事务来完成

而本地缓存是多节点、短 TTL 的、如果参与写操作会带来数据不一致甚至超卖的问题

所以我们在架构上是明确做了读写分离：本地缓存只负责读路径优化、写路径完全交给下游系统处理









# 为什么设置本地缓存过期时间为 5s



我们设置本地缓存过期时间为 **5秒、**是经过权衡后做出的选择、主要考虑四方面：

1. **内存占用率**：本地缓存不能太大、否则堆内存占用过高、会影响服务稳定性。
2. **GC情况**：如果缓存时间过长、比如 10秒、缓存对象会在新生代多次 Minor GC 后晋升到老年代、占满老年代空间、触发 Full GC。Full GC 开销大、会暂停所有应用线程、对高并发服务影响严重。
3. **缓存命中率**：如果缓存时间过短、比如 1秒、高峰期缓存可能刚写入就失效、大量请求直接打到 Redis 上、命中率低、无法有效保护 Redis、也解决不了热 Key 问题。
4. **数据一致性**：缓存时间太长可能导致脏数据存在时间过久、需要结合业务需求控制



首先说一下 10s。**时间太长（如10秒）**：虽然命中率高、但会导致JVM内存占用过高、会导致大量对象长期驻留在堆内、无法被及时回收、从而占满老年代空间、频繁触发 垃圾回收Full GC、影响服务稳定性。同时、数据一致性延迟更长



然后是设置为 1s：内存占用低、但对于持续几秒的流量高峰、缓存可能刚写入就失效了、导致大量请求击穿本地缓存、打到Redis上、缓存命中率不理想、没有起到很好的保护Redis 的作用、同时没有很好的解决热 key 问题



所以我们压测后选择了 5s、这个是一个权衡后的选择

它能将内存占用稳定在可接受的范围（50%-60%）、**GC稳定**、同时命中率也达到了很高的水平（接近97%）









# 本地缓存的key 和 value是什么



主要是域名的基础信息、黑白名单结果、或者一些是否可访问的标志位

这些都是读多写少、允许短时间不一致的数据





**我们本地缓存存的主要是黑白名单查询结果和域名访问相关的只读数据。key 不是只有域名维度、也包括 IP 维度和部分组合规则维度。比如：**

- `whitelist:domain:{domain}`
- `blacklist:domain:{domain}`
- `blacklist:ip:{ip}`
- `rule:{domain}:{ip}` 这种组合维度结果

**value 一般不是特别复杂、核心是某个对象是否命中黑名单/白名单、命中的规则结果、以及对应的一些基础信息或标志位。它们都属于读多写少、允许短时间不一致的数据**



域名本身量确实不大、稳定在几千/几万级、单纯域名缓存占用很小

真正容易把缓存规模和对象 churn 拉起来的是 IP 这种高基数 key——在恶意刷接口场景下、不同 IP 的数量可能在短时间内快速膨胀

本地缓存的价值不只是省 Redis、而是吸收尖刺流量



所以我们在 SDK 层引入本地缓存主要是为了解决热点与突发流量、把对 Redis 的热 key 压力分摊到各个应用实例内存里、同时 TTL 不能太长、否则在高并发下大量对象跨多个 Minor GC 周期存活、出现晋升和 GC 抖动风险。压测后我们选择 5 秒作为命中率、稳定性和一致性延迟之间的折中





# 为什么会出现 Redis 热 key 的问题、热 key 是什么、会带来什么问题



热 Key 指的是在 Redis 中在短时间内**极高频访问的某个 Key、**比如 QPS 里 80% 都打在这个 Key 上。

**为什么会出现热 Key？**  
 本质原因是**访问分布不均（数据倾斜）、**典型场景有：



 第一是业务热点、比如秒杀商品或热门数据、大量请求集中访问同一个 Key

 第二是缓存设计不合理、比如黑白名单或配置数据全部放在一个 Key

 第三是缓存粒度过粗、导致所有请求打在同一个 Key

 第四是突发流量或攻击导致某个 Key 被打爆

**问题本质：**  
 👉 单点 Key 成为瓶颈 → 打爆单个 Redis 实例的 CPU / 网络 / IO



问题就是大量请求打到同一个 key 会导致 Redis 的单点 QPS 飙升、甚至成为瓶颈。还有可能会带来缓存击穿、穿透等问题。以及就是系统负载不均衡、请求会集中到某一个节点、导致这个节点过载、而其他的节点会比较空闲。



分散 key 的情况下、请求会在多个 key、多个节点之间分摊、系统是水平扩展的

 而热 key 场景下、本质是所有请求集中到单个 key、对应单个节点、形成单点瓶颈、无法利用集群能力









# 假如说十万个求打到分散的 key 和这个十万个请求打到就一个 key 有什么区别



这两种情况**本质区别很大**：

- 如果是 **10 万请求打到 10 万个不同的 Key、**流量是分散的、请求会均匀分布在不同 Key 上、Redis 可以并发处理、整体压力是可控的
- 但如果是 **10 万请求打到同一个 Key（热 Key）、**那所有请求都会集中到同一个数据上、虽然 Redis 是单线程处理命令、但这个 Key 会成为热点、导致 CPU、网络、带宽都集中在这里、容易成为单点的瓶颈











# Redis 明明能扛 10 万 QPS、为什么还要本地缓存





**不是 Redis 理论 QPS 不够、而是`热点 key、突发流量、长尾 RT 和链路隔离`问题、让单用 Redis 不够稳**

可以这样答：

**Redis 平均抗 10 万 QPS、这是一个比较理想化的整体吞吐指标、但实际业务里不能只看总 QPS、还要看访问分布是否均匀**



**我们的问题不是所有 key 都平均访问、而是存在明显的热点 key 和流量尖刺**

**某个热点名单或者热点规则结果、可能在短时间内被大量重复访问、这会导致单 key 访问集中、Redis RT 出现长尾、进而阻塞其他正常请求**



**另外如果热点 key 对应的数据对象本身比较大、还会叠加大 key 带来的网络传输和反序列化开销、形成连锁放大**

**所以即使 Redis 总体 QPS 还没打满、我们也可能已经在热点 key 上看到明显瓶颈了**

**这个时候引入本地缓存、目的不是替代 Redis、而是把热点读流量分摊到各个应用实例内存里、进一步降低 Redis 压力和长尾**

# 如何保证一致性面试回答



**三重方案**：更新 DB 时发消息到 NQ 异步更新 Redis、监听 DB 的 `binlog` 进行增量对账修复、以天为维度定时全量扫描数据与 Redis 对比修复。



**第一、通过MQ消息队列实现准实时同步**

在核心业务流程中、当运营人员通过后台（数据库）更新黑名单状态时、我们会采用写DB后立即发送MQ的异步化方案。也就是说、在更新完数据库之后、我们会立刻向消息队列发送一条变更通知、我们有一个独立的**缓存同步服务、**它会订阅这个MQ主题、当它收到变更消息后、会立即去更新**Redis缓存。这是我们保证数据一致性的第一层**



这样做的最大好处是、**主业务流程和缓存更新完全解耦、**保证了API接口的低延迟和高吞吐量。同时我们利用MQ本身具备的**持久化和失败重试**机制、确保了缓存更新的通知能够可靠送达



**第二、通过监听数据库Binlog进行增量校对**

为了防止第一层出现代码Bug或消息丢失等极端情况、我们部署了一套独立的对账系统。它的核心原理是**订阅并解析数据库的Binlog日志**——会记录所有的数据变更。一旦监听到数据变更、它会立刻主动与Redis中的数据进行比对。如果发现数据不一致、它会**强制以数据库为准进行修复**

这一层确保了任何来源的数据库变更、这是我们保证数据准确性的第二层





**第三、通过每日全量任务作为最终兜底**

我们有一个定时任务、以天为维度定时全量扫描数据与 Redis 对比修复。会在每天凌晨的业务低峰期、**扫描前一天发生变更的所有数据、**进行一次**全量的DB-Redis数据比对**



这个过程不仅能修复前两层可能遗漏的任何细微差错

**如果修复任务连续失败并达到我们设定的阈值、就会**触发高级别告警、通知人工介入、这套机制确保了系统具备自我审计和异常发现的能力、保证了在业务方真正使用时、数据是100%可靠的





# 那多个请求同时到 Redis 时、本地缓存怎么更新？



用的是旁路缓存



##  Cache Aside（旁路缓存模式）

**读：**

- `先查缓存 → miss → 查 DB → 回填缓存`

**写：**

- `更新 DB → 删除缓存`









**如果多个请求同时访问 Redis、你们本地缓存怎么更新呢？**

他真正想问的是 **缓存重建时的并发控制**、也就是：

- 本地缓存过期后
- 大量请求同时发现本地缓存没命中
- 都去打 Redis
- 那么谁来回填本地缓存？
- 会不会很多请求一起回填、造成击穿/抖动？

你原来的回答又绕回了：

- 本地缓存拦 hot key
- Redis incr
- DB 扣减

这个其实已经**偏题了**。  
因为他现在问的不是业务扣减链路、而是**本地缓存 miss 之后的重建机制**。

---

这个问题应该怎么理解

其实Redis 怎么更新到本地缓存并不是 Redis 主动推给本地缓存

更常见的是：

**本地缓存过期 → 请求打到服务实例 → 服务实例查 Redis → 拿到结果后**

**由当前这个请求线程把结果回填到本地缓存**

也就是说：

- **不是 Redis 更新本地缓存**
- 而是**应用在访问 Redis 后、把结果写回本地缓存**

这叫：

**Cache Aside / 旁路缓存模式**

---

那多个请求同时到 Redis 时、本地缓存怎么更新？

一般有两种回答方式：

**方案一：简单版**

如果你们业务里本地缓存 TTL 很短、数据结构简单、而且 Redis 扛得住、那么可以直接说：

**本地缓存过期后、如果多个请求同时 miss、本质上都会去访问 Redis、拿到结果后再各自尝试写回本地缓存**

**因为写入的是同一份值、所以即使存在短时间重复回填、问题也不大**

**我们这里本地缓存的核心目标是抗热点、削峰、而不是做严格的单 `flight` 控制、所以实现上没有做复杂的并发锁、而是接受少量并发回源**

这个回答很真实、也比较符合你前面`5 秒 TTL、不主动更新`的设计。

---

方案二：进阶版

如果想答得更专业、可以补一句优化手段：

**为了避免本地缓存失效瞬间大量请求同时打 Redis、、可以在单机内部加一个互斥控制、比如 mutex / `singleflight`**

**这样同一个 key 过期后、只让一个线程去 Redis 拉最新值、其他线程等待这个结果、然后共享同一次重建结果、再一起读本地缓存。**



你这个项目怎么说最合适、结合你前面的描述、我建议你这样答：

**一分钟面试回答版**

**我们本地缓存不是由 Redis 主动更新的、而是在本地缓存 miss 之后、由请求线程去 Redis 读取最新值、再回填到本地缓存**

**也就是说、更新动作是在应用侧完成的**

**并发场景下、如果多个请求同时发现本地缓存过期、最简单的做法是它们都会访问 Redis、拿到结果后再写回本地缓存、因为写的是同一份数据、所以即使有少量重复回填也可以接受**

**进一步优化的话、可以在单机内部对热点 key 加互斥锁或者 `singleflight`、只让一个请求去 Redis 拉数据、其他请求复用结果、避免瞬时并发击穿 Redis**





**简洁版**

**我们本地缓存不做主动推送更新、而是被动回填。也就是本地缓存 miss 之后、请求线程去 Redis 读取最新值、再把结果写回本地缓存。并发情况下、如果多个请求同时 miss、都会访问 Redis 后尝试回填、因为是同一份数据、少量重复写问题不大。对于热点 key、还可以加 `singleflight` 或本地锁、避免大量并发同时回源**



更像面试回答版

**本地缓存不是 Redis 主动更新的、而是采用` cache aside `模式：本地缓存过期后、请求线程查 Redis、查到后再回填本地缓存**

**多个请求同时 miss 时、基础实现可能会出现并发访问 Redis、重复回填本地缓存的问题、但因为值一致、通常可接受**

**若要进一步优化热点 key 场景、可以通过 `singleflight`、互斥锁或者双重检查机制、控制同一 key 只由一个线程回源并更新本地缓存、其余线程复用结果**











# **订阅 MQ 消息更新 Redis 后、Redis 缓存是永不过期还是会定期过期？那你的这刚刚这个 5 秒的策略指的是本地缓存、然后我们 Redis 有没有过期策略？那如果 Redis 过期了、谁再来写？ 那这里面会可能会有个风险、就是说你的缓存其实有可能说最长（24 小时失效）…… 万一有一天某个域名突然变火了、那会不会有一个流量异常的情况？**



我们在设计 Redis 缓存策略时、没有采用单一过期方案、而是根据数据访问特征做了区分。

- 对**普通数据（99%）、**我们采用 **定期过期（24小时+随机值）**。  
 这样做有三点考虑：  
 一是作为**兜底机制、**防止 MQ 或 Binlog 更新链路出现异常导致永久脏数据  
 二是**节省内存、**避免冷数据长期占用  
 三是**随机TTL**可以防止大量 Key 同时失效引发缓存雪崩

当 Redis 的缓存过期时、会触发**回源机制**：

- 如果是普通数据、就从数据库中回源、`然后再写回 Redis`



- 对**极度热门且稳定的数据（<1%）、**比如公司核心域名、我们采用 **永不过期策略**。
- 比如 `tencent.com` 的解析记录、或 `习近平.com` 这种永久合规黑名单）、它们在Redis里被设置的是永不过期  
 这类数据访问量极高、更新频率极低、而且依赖于主动更新的机制（MQ 或 Binlog 推送）、这些数据非常稳定且更新路径完全可控、我们信任主动更新机制、用永不过期换取极致性能和稳定性。



针对突然变热的场景、比如某个域名突然流量暴涨、我们会监控 Redis 命中率和访问量、一旦发现访问量突增、会**自动提升这类 Key 的缓存等级、**比如延长 Redis 过期时间、甚至提升为永不过期 + 主动更、防止缓存击穿和流量抖动。

这样、本地缓存保证短时高性能、Redis 缓存保证全局一致性、两者配合可以在高并发下平滑应对热点

# **引入本地缓存解决热 Key 问题**



针对上述问题、我在设计这个黑白名单系统时、核心的考虑就是如何规避热Key风险

每个实例只用处理一小部分流量、从而完美地解决了单点瓶颈问题













# **为什么本地缓存可以解决热 Key 问题？**





这个问题的核心在于理解热Key问题的本质：**请求的集中化**。

- **没有本地缓存时**：设想一下、你有100台应用服务器。当一个热Key出现时、这100台服务器上的所有相关请求都会跨越网络、集中轰炸后端单一的Redis节点（或分片）

  - Redis的单线程模型决定了它必须排队处理这些请求、这就形成了瓶頸。
  - **模型**：`[服务器1, 服务器2, ..., 服务器100] ---> [单一Redis节点]` = **拥堵**
- **引入本地缓存后**：我们将战场从中心分散到了地方

  - **请求拦截**：第一个请求穿透到Redis、获取数据后、会立刻在**当前这台服务器的JVM内存中**缓存一份
  - **压力分散**：在接下来的缓存有效期内（比如我们定的5秒）、所有访问这个热Key的请求、都会被这100台服务器**各自的本地缓存**所拦截和响应。请求根本不会离开服务器去访问`Redis`
  - **模型**：
  
    - `请求 -> 服务器1 [本地缓存命中！]`
    - `请求 -> 服务器2 [本地缓存命中！]`
    - `...`
    - `请求 -> 服务器100 [本地缓存命中！]`
    - 最终、Redis在5秒内可能只收到了一次请求

**一句话总结：**

**本地缓存通过将对单一节点的集中式压力、分散到各个应用服务器实例内部进行处理、从而化解了热Key的单点瓶颈**







# **介绍一下多级缓存架构**



本地缓存解决热Key问题的方案、本身就是多级缓存架构（Multi-level Caching）的典型体现

这套架构通常至少包含两个层级：

1. **L1 Cache (一级缓存): 应用内/本地缓存 (In-Process/Local Cache)**

   - **实现方式:** 直接在应用服务器的JVM内存中实现、例如使用一个`ConcurrentHashMap`、或者更专业的库如Guava Cache、Caffeine
   -  这是解决热Key问题的核心。它作为第一道防线、将绝大多数对热Key的读请求直接在内存中消化掉、避免了网络IO和对后端集中式缓存的冲击。它的特点是**速度最快、访问延迟最低、**但容量有限且数据在多个服务器实例间不一致
2. **L2 Cache (二级缓存): 集中式/分布式缓存 (Centralized/Distributed Cache)**

   - **实现方式:** 独立的缓存服务、如Redis、Memcached。
   - 当L1本地缓存未命中时（例如、服务刚启动、缓存已过期或数据是冷数据）、请求会穿透到L2的Redis
   - Redis作为所有应用服务器共享的缓存层、保证了数据的一致性、并承担了保护后端数据库的职责。它的速度远快于数据库、但慢于本地缓存









# **你会选择用Guava还是Caffeine呢？结合业务说一下**



**我会选择 `Caffeine`。**

虽然Guava Cache是一个非常优秀且经过长期验证的本地缓存库

但Caffeine在设计和性能上被认为是Guava Cache的下一代、是更现代、更优的选择

结合我们这个需要处理热Key的高并发业务场景、选择Caffeine的理由如下：



**核心优势：更优的缓存命中率和性能**

Caffeine最核心的优势在于它采用了 **W-TinyLFU (Window TinyLFU)** 缓存淘汰算法

这是一个非常精妙的设计、特别适合我们的业务场景。

- **业务场景分析：**

  - 我们的系统不仅有**突发性的热点**（例如某个商品秒杀活动开始、其ID在短时间内成为热Key）、也有一些**长期稳定访问的热点**（例如首页配置信息）
  - 传统的 **LRU (Least Recently Used)** 算法（Guava Cache的近似实现）在这种场景下表现不佳。它可能会因为一次突发的数据扫描（例如一个后台任务遍历了很多数据）、就把那些长期稳定访问的热点数据给淘汰出去、这被称为缓存污染、当真正的用户请求再次访问这些长期热点时、就会发生缓存穿透、压力给到Redis。
- **Caffeine (W-TinyLFU) 如何解决：**

  - **LFU (Least Frequently Used) 特性:** W-TinyLFU算法的核心是LFU、它会跟踪每个Key的访问频率
  - 这意味着、那些被**频繁访问**的长期热点数据、即使最近没有被用到、也不容易被淘汰
  - 这完美地保护了我们的稳定热点数据、保证了高命中率。
  - **Window 特性:** 纯粹的LFU有一个问题、就是新加入的Key因为频率低、很难在缓存中存活下来、即使它即将成为新的热点。Caffeine的Window部分就像一个新手保护区（类似一个小的LRU空间）、让新来的数据有机会在短期内被多次访问、积累它的频率、从而有机会进入主缓存区、这保证了系统能够**快速适应新的热点**



**对业务的直接价值**

1. **更高的缓存命中率:** W-TinyLFU算法在真实世界的各种访问模式下、提供了近乎理论最优的缓存命中率。在我们的场景中、**更高的命中率意味着**：

   - **更少的Redis请求：** 直接降低了网络开销和Redis的负载
   - **更低的响应延迟：** 更多的请求在JVM内部以微秒级完成
   - **更强的系统稳定性：** 后端服务（Redis、DB）得到了更好的保护
2. **极致的并发性能:** Caffeine在并发读写性能上做了大量优化、其吞吐量远超Guava Cache
3. 在一个需要支撑成百上千个线程同时访问缓存的高并发服务中、Caffeine的低锁竞争和高吞t量能够确保本地缓存本身不会成为新的性能瓶颈



- **Guava Cache** 是一个好的选择、它稳定可靠、功能齐全。如果项目是老项目、已经深度集成了Guava、维持现状也是可以接受的。
- **Caffeine** 则是一个更好**的选择。对于新项目、或者对性能有极致追求的现有项目、我都会**毫不犹豫地选择Caffeine、因为它提供的更高命中率和并发性能、能直接转化为更低的系统延迟、更少的后端负载和更节约的服务器成本、这与我们应对热Key问题的初衷完全契合
- 它在技术上的先进性、能为业务带来实实在在的收益





# **引入本地缓存会引入什么新的问题吗？**



这是面试中必考的权衡（Trade-off）问题。引入任何技术都会带来新的挑战：

1. **数据一致性问题（最主要的问题）**：

   - 本地缓存是Redis/DB中数据的副本、当源头数据（比如DB里的黑名单状态）被修改后、各个服务器上的本地缓存**不会立刻知道**。在缓存过期之前、它会一直是脏数据、这就导致了数据的不一致、可能会在短时间内把一个已经被解封的正常用户给拦住
2. **内存占用与GC压力**：

   - 本地缓存是直接存储在**JVM堆内存**中的。如果缓存数据量巨大、或者没有合理配置最大容量、就会消耗大量内存、挤占了业务逻辑本身需要的内存空间、甚至可能引发频繁的GC（垃圾回收）、影响应用性能。
3. **服务重启与缓存冷启动问题**：

   - 当某台应用服务器重启时、它的本地缓存是空的
   - 此时如果大量请求涌入、这些请求会全部穿透本地缓存、直接打向Redis、可能瞬间给Redis带来压力
   - 这个过程叫做缓存的冷启动







# **缓存时间过长/过短有什么问题吗？**



这是对5秒策略的深度追问、考察你对权衡的理解。

- **缓存时间过短（比如1秒）**

  - **优点**：数据一致性好、数据最多只脏1秒。内存占用低
  - **缺点**：**缓存命中率会显著降低**。对于持续几秒的流量洪峰、缓存可能刚建立就失效了、导致大量请求还是会穿透到Redis。这样本地缓存就**失去了保护后端的意义、**起不到解决热Key问题的效果
- **缓存时间过长（比如1分钟）**

  - **优点**：**缓存命中率非常高**。能非常有效地保护后端Redis。
  - **缺点**：
  
    - **数据一致性差**：数据最多可能脏1-2分钟、对于某些业务场景（比如实时解封用户）是不可接受的
    - **内存占用高与GC风险**：更长的时间意味着更多的Key会同时存在于内存中、增加了JVM堆内存的压力、也增加了GC的频率和单次回收的时间

**结论：5秒是我们基于压测数据、在高命中率、可接受的一致性延迟和稳定的内存占用三者之间找到的最佳平衡点。**









# **本地缓存命中率高或者低有什么影响吗？**



- **高命中率（比如我们达到的97%）**

  - **正面影响**：
  
    - **性能极佳**：绝大多数请求直接由内存响应、用户感受到的延迟极低。
    - **后端稳定**：后端Redis和数据库得到了充分的保护、系统非常稳定、能够从容应对流量洪峰。
    - **成本节约**：降低了对后端昂贵资源（如高配Redis集群）的依赖。
  - **潜在负面影响**：如果高命中率是通过设置**过长的缓存时间**或**无限制的缓存容量**换来的、那么它可能伴随着高内存占用和数据不一致的风险
- **低命中率**

  - **负面影响**：
  
    - **本地缓存失效**：意味着本地缓存这个设计是失败的、它没有起到应有的作用。
    - **性能瓶颈**：大量请求穿透到Redis、系统响应慢、热Key问题依然存在
    - **资源浪费**：本地缓存本身占用了内存、并且CPU在计算和维护它时也有开销、但却没有带来收益、纯属负资产







# **本地缓存是JVM层面的缓存吗？**



**是的可以这么理解。**

更准确地说

我们通常使用的本地缓存库（如Google Guava Cache、Caffeine）是在**JVM的堆内存（Heap Memory）中**创建和管理数据

- 缓存的Key和Value、以及缓存容器本身、都是Java对象、它们和其他业务对象一样、**都存储在堆内存里**
- 它们的生命周期由JVM的垃圾回收器（Garbage Collector）管理
- 当一个缓存项过期或被淘汰后、它所占用的堆内存会在下一次GC时被回收
- 这种缓存在应用进程（JVM进程）之内、所以也叫**进程内缓存（In-Process Cache）**





# **命中率过高会有可能导致GC吗？是什么GC？一定会导致GC吗？一定会导致Full GC吗？**



这是一个非常好的递进问题、能充分展示你对JVM的理解深度

1. **命中率高本身不会导致GC**：

   - 命中率只是一个衡量缓存效率的**结果指标**
   - 真正与GC相关的是**缓存的写入（`put`）和对象的存活时间**
   - 一个高命中率的缓存、往往意味着它存储了大量被频繁访问的数据
   - 这个存储大量数据的行为、才是和GC相关的
2. **会导致什么GC？**

   - **主要是Young GC（Minor GC）**
   - 当新的数据被写入缓存时、这些Key-Value对象通常是在JVM的**新生代（Young Generation）的Eden区**分配的。当Eden区满了、就会触发一次Young GC
   - 在设计良好的系统中、Young GC是频繁发生且非常快速的、对应用影响很小。
   - 如果缓存中的对象在多次Young GC后依然存活（因为还没过期）、它们会被晋升到**老年代（Old Generation）**。
3. **一定会导致GC吗？**

   - **不一定**
   - 一次缓存的命中（`get`）或写入（`put`）操作、本身不一定会立刻触发GC
   - GC的触发时机是当JVM的某个内存区域（主要是Eden区）满了、需要回收空间来分配新对象时
   - 缓存操作只是众多对象分配行为中的一种、它会贡献于填满内存区域、从而最终促成GC的发生
4. **一定会导致Full GC吗？**

   - **绝对不一定、而且是应该极力避免的**
   - **Full GC（Major GC）** 的触发通常是因为**老年代空间不足**
   - 一个**设计良好**的本地缓存、会通过设置**最大容量限制**和**合理的过期时间、**来确保大部分缓存对象在新生代就被回收掉、或者即使晋升到老年代、也不会将老年代填满。
   - 只有在**设计糟糕**的情况下、比如缓存容量不设上限、或者缓存时间过长、导致大量老不死的对象持续晋升并最终耗尽老年代空间、才会频繁触发**Full GC**
   - Full GC会导致长时间的Stop-The-World、让应用程序完全卡死、这是生产环境中的大忌



**总结一下面试话术**：

一个高命中率且设计良好的本地缓存、其对象的生命周期主要与快速的Young GC相关

本身不应该、也绝不能成为频繁触发Full GC的原因

控制缓存的最大容量和过期时间、是防止其影响老年代稳定性的关键













# 为什么缓存时间长会导致 Full GC？



## 总结

本地缓存时间过长会直接影响对象在 JVM 堆中的生命周期。JVM 堆分代管理、新创建的对象先分配到新生代（Eden区）、Minor GC 会频繁清理短命对象。

如果缓存过期时间长、比如 10 秒、缓存对象会在 Eden 和 Survivor 区长期存活、多次 Minor GC 仍然存活、就会被晋升到老年代。老年代空间本身有限、如果这些长期存活的缓存对象占满老年代、新对象无法正常晋升、Minor GC 就清不出足够空间。

这时 JVM 会触发 **Full GC** 来尝试清理老年代、但大部分缓存对象仍然被引用、回收效果有限

Full GC 开销大、会暂停所有应用线程（Stop-The-World）、对高并发服务影响非常严重。







这个问题是理解本地缓存权衡的**底层 JVM 原理关键点**。

我们来分两步说清楚：**（1）为什么缓存时间长会影响 GC（2）为什么甚至可能触发 Full GC。**



**一、为什么缓存时间「长」会影响 GC？**



当你把本地缓存时间设置得很长（比如10秒、1分钟）时、核心问题是：



> 缓存在内存中驻留的对象会越来越多、生命周期也会更长。

**对象无法被及时回收**

- JVM 的垃圾回收是以是否还被引用为依据的
- 本地缓存（如 Caffeine、Guava Cache）内部通常是一个 `ConcurrentHashMap` 或类似结构。
- 一旦你把对象放进缓存里、并且它还没过期、那么引用就仍然存在（缓存的 Map key/value 在指向它）。
- 这样、这些对象在 GC 的可达性分析中**仍然是活对象、**不会被清除

所以：缓存时间越长、对象在堆中存活的时间越久、被回收的机会越少。



**堆空间被持续占用**

随着更多的请求进入、更多的 Key 被缓存：

- 堆中缓存数据越来越多
- 老年代（Old Generation）中被晋升的对象越来越多

最终导致：

- 年轻代GC（Minor GC）清不出多少空间
- 老年代空间紧张







**二、为什么会导致** **Full GC？**



Full GC 触发的典型原因之一就是：

> 老年代空间不足、JVM 无法为新的对象分配空间。



而长时间缓存的对象（长期存活）正是老年代的产生原因



**对象晋升**



JVM 的 GC 一般分代管理：

- 新生代：存放新建的短命对象
- 老年代：存放多次 GC 仍然存活的对象。

当你缓存时间较长时：

- 这些缓存对象会多次经历 Minor GC
- 每次都存活下来
- 最终晋升到老年代

于是老年代空间被占满、无法为新对象留出位置、**触发 Full GC**





 **Full GC 带来的问题**

Full GC 代价非常高

- 会暂停所有应用线程（Stop The World）
- 可能持续几十毫秒到几秒
- 如果频繁发生、整个应用响应时间会抖动、性能下降。

所以当缓存过多、对象太久不回收时、就容易出现：



> **内存占用高 + Full GC 频繁 + 服务卡顿甚至OOM。**







> 本地缓存时间设置太长、会导致大量对象长期驻留在堆内、无法被及时回收、从而占满老年代空间、频繁触发 Full GC、而合适的过期时间（比如5秒）则能在命中率和GC负担之间取得平衡。





你这个追问正是很多人理解 GC 时容易卡住的地方

为什什么缓存时间长、对象就会导致「老年代空间占满」。

---



**一、先理解「对象晋升」的本质**



JVM 的堆是分代的：

- **新生代（Young Generation）**：专门放刚创建、生命周期短的对象。
- 比如临时字符串、请求参数、计算中间结果。
- **老年代（Old Generation）**：放长期存活的对象。





**GC 的策略**：



> 如果一个对象多次经过 Minor GC（新生代回收）依然还活着
> 
> JVM 认为它是长期存活的、就会把它晋升到老年代



---



**二、缓存对象为什么容易晋升？**



举个例子：



假设我们在应用中有一个 Caffeine 缓存、过期时间设置为 **10秒**。

当某个请求把数据放入缓存后：

- 这个对象会在堆中至少存活 **10秒**
- 在这 10 秒里、JVM 至少会触发几次 Minor GC；
- 每次 GC 扫描时发现这个对象还活着（因为缓存 Map 还在引用它）
- JVM 会提升它的年龄计数（age）
- 一旦达到阈值（比如 MaxTenuringThreshold、默认15）、就会被晋升到老年代



>  换句话说：缓存时间越长、对象越有可能活太久、从而**被认为是长期对象、放入老年代**。



---



**三、为什么老年代会被占满？重要**

继续上面的例子：

1. 每次请求都会往缓存里放新对象
2. 老的缓存对象因为设置了 10 秒 TTL、一时半会不会被淘汰
3. 新的请求又放入新的缓存项；
4. 于是：

- 新对象不断创建（进入新生代）
- 旧对象仍然被引用（已经在老年代）



结果：**老年代的对象越来越多、几乎不被释放**。



直到：

- 老年代可用空间不足
- JVM 需要清理
- 但很多缓存对象还没过期、还在被引用
- **清理不了 → Full GC 被触发**



**四、为什么 Full GC 很容易频繁触发**

因为 Full GC 是老年代空间不足的最后手段。



当老年代被缓存对象长期占满时

- Minor GC 清不出空间
- JVM 无法在新生代分配新对象
- 于是触发 Full GC 去尝试清理老年代
- 但大多数缓存对象仍然被引用、清理效果有限
- 导致 Full GC 越来越频繁
- 最终可能 OOM（java.lang.OutOfMemoryError: GC overhead limit exceeded）。







> 缓存时间太长会让缓存对象长期存活、频繁晋升到老年代、而老年代空间又不像新生代那样容易回收、所以会被这些长生命周期的对象逐渐占满、最终导致 Full GC 的频繁触发和性能下降













## **为什么本地缓存的过期时间长短会影响GC？**



要回答这个问题、我们首先要理解一个核心概念：**JVM的垃圾回收是分代的（Generational GC）**。

一个Java对象（比如我们缓存的Key-Value对）在JVM的堆内存中、会经历一个“从小到大”的旅程：

1. **出生地：新生代 (Young Generation)**

   - 几乎所有新创建的对象、都会被分配在新生代的`Eden`区。
   - 新生代有一个特点：**GC非常频繁、但速度极快、**这种GC叫做**Minor GC**。
   - Minor GC的目标就是快速清理掉朝生夕死的对象。
2. **晋升之路：幸存区 (Survivor Spaces)**

   - 当`Eden`区满了、触发Minor GC时、还存活的对象（即还有代码在引用它）会被移动到`Survivor`区
   - 对象每在Survivor区成功幸存一次Minor GC、它的年龄（Age）就会+1
3. **老年代 (Old Generation)**

   - 当一个对象的年龄达到一个阈值（比如默认是15岁）、JVM就会认为它是一个长期存活的对象、并将它从新生代**晋升（Promote）到老年代**
   - 老年代的特点是：**GC不频繁、但一旦发生、耗时很长**。这种GC叫做**Major GC**或**Full GC**

**现在我们把缓存的过期时间放进这个模型里：**

- **当缓存时间设置得很短时（比如我们的5秒）：**

  - 一个缓存对象在`Eden`区出生。
  - 在接下来的5秒内、它被频繁访问、所以它是存活的。
  - **5秒后、缓存过期了**。我们的缓存库（比如Guava Cache）会移除对这个对象的强引用
  - 下一次**Minor GC**发生时（通常很快就会发生）、垃圾回收器发现这个对象已经没有任何引用了。
  - **结果**：这个对象**在新生代就被回收了**。它根本没有机会变老、更不会被晋升到老年代。这对GC系统的影响非常小、就像清理日常垃圾一样轻松
- **当缓存时间设置得很长时（比如10分钟）：**

  - 一个缓存对象在`Eden`区出生。
  - 在接下来的10分钟内、**无数次Minor GC发生了**。
  - 由于缓存还没过期、这个对象始终被缓存库强引用着、所以它每次都能在Minor GC中幸存来。
  - 它的年龄不断增加（1岁、2岁、...、15岁）。
  - **结果**：最终这个对象达到了晋升阈值、**被晋升到了老年代**。它变成了一个长期占用老年代空间的对象。

结论：

缓存过期时间的长短、直接决定了一个缓存对象是短命对象还是长命对象

短命对象在高效的新生代被处理掉

而长命对象则会不断地被晋升到老年代、持续不断地给老年代带来内存压力







## **为什么这会导致Full GC？**



这部分是上面逻辑的自然延伸、是一个因果链条。

1. **老年代空间被持续填充**：

   - 当缓存时间设置过长、会有源源不断的缓存对象从新生代晋升到老年代。
   - 同时如果你的缓存没有设置最大容量（size limit）、或者容量设置得非常大、老年代的空间就会被这些长寿的缓存对象迅速填满。
2. **触发Full GC**：

   - 当老年代的空间不足以容纳新晋升上来的对象、或者达到某个占用率阈值时、**JVM就不得不触发一次Full GC**。
   - Full GC的目标是清理整个堆内存、尤其是老年代。
3. **Full GC的灾难：`Stop-The-World(STW)`**

   - Full GC是JVM中开销最大的操作。为了保证垃圾回收的正确性、JVM在执行Full GC时、必须**暂停所有正在运行的应用程序线程**。这个过程就叫做Stop-The-World” (STW)
   - 在STW期间、你的应用程序是**完全卡死**的。它无法响应任何用户请求、无法处理任何业务逻辑。对于一个像我们这样的高并发域名服务来说、哪怕只有几百毫秒的STW、也可能导致大量的API请求超时、引发连锁反应、甚至造成系统雪崩
4. **恶性循环**：

   - 更糟糕的是、如果老年代里大部分都是**仍然有效的、未过期的长寿缓存对象、**那么这次代价高昂的Full GC可能**回收不了多少内存**。
   - 这就会导致老年代空间很快又满了、从而在短时间内**频繁触发Full GC、**让你的应用程序反复陷入卡死-恢复-又卡死的恶性循环中、直到最终因`OutOfMemoryError`而崩溃。

**总结面试话术：**

本地缓存的过期时间直接决定了缓存对象的生命周期

**设置过长会导致大量缓存对象在多次Minor GC后依然存活、最终被晋升到JVM的老年代**

这种持续的晋升会不断填充老年代空间、一旦老年代被占满、就会**触发开销极大的Full GC**

Full GC会带来Stop-The-World、导致应用程序在短时间内完全失去响应、对我们这种高并发服务是致命的

因此合理地设置缓存过期时间和最大容量、确保缓存对象能尽可能在新生代就被回收、是防止Full GC、保障服务稳定性的关键所在

本地缓存时间过长会直接影响对象在 JVM 堆中的生命周期。JVM 堆分代管理、新创建的对象先分配到新生代（Eden区）、Minor GC 会频繁清理短命对象。

Full GC 开销大、会暂停所有应用线程（Stop-The-World）、对高并发服务影响非常严重

1. **为什么时间需要足够长以保证性能？ (抗住热点冲击)**

将时间设置为5秒而不是更短（比如500毫秒或1秒）、核心目标是为了**最大化地吸收和分散热点流量、保护后端系统**。

让我们用数据来量化这个场景：

- **业务背景：** 某个商品因为一场活动突然成为热点。
- **流量模型：** 在活动高峰期、这个商品Key的QPS（每秒请求数）可能高达 **10,000**。
- **系统架构：** 100台应用服务器实例、后端是Redis集群

现在我们对比不同的过期时间：

- **情况A：没有本地缓存**

  - 所有10000 QPS直接涌向Redis
  - Redis的单线程模型在这种集中的单Key轰炸下会立刻达到瓶颈、CPU飙升至100%、导致所有相关请求超时、甚至可能拖垮整个Redis实例、引发雪崩效应。**这是灾难性的**
- **情况B：本地缓存过期时间设置为1秒**

  - 在第一秒的开始、第一个请求会穿透到Redis。
  - 在接下来的一秒内、所有请求（近10,000个）都会被100台服务器的本地缓存命中、Redis安然无恙。
  - **问题在于：** 1秒钟之后、100台服务器上的本地缓存**几乎同时失效**
  - 此刻每台服务器都会有新的请求涌入、它们都会去请求Redis
  - 这会导致一个微型的请求风暴：**瞬间有100个并发请求涌向Redis**
  - 虽然比10000 QPS好得多、但这依然是一个不小的冲击、并且会每秒重复一次
  - 这被称为缓存雪崩的微观体现



- **情况C：本地缓存过期时间设置为5秒 (我们的选择)**

  - 在第一个5秒周期内、情况和上面一样、几乎所有请求都被本地缓存拦截、Redis负载极低（可能只有一个请求）。
  - **关键区别在于：** 在5秒之后、虽然缓存也会过期、但由于将冲击分散到了一个更长的时间窗口里、**后端Redis在5秒内只需要处理大约100个请求、**平均下来QPS只有 **20** (`100 req / 5s`)。
  - 这个负载对于Redis来说是**微不足道**的
  - 5秒的窗口给系统提供了充足的缓冲

**结论：** 5秒的长度足以确保在一个热点事件的完整生命周期内（通常热点也是以秒为单位爆发）、绝大部分（99.9%以上）的请求压力被前端服务器集群均摊、从而有效地保护了后端的集中式服务。

# 如何保证一致性



**面试官：你的架构里用了这么多级缓存、那你是如何保证数据一致性的呢？**



在设计这个系统之初、数据一致性就是我们考虑的最高优选级之一

因为风控系统的策略如果出现数据不一致、可能会导致错放或错杀、后果非常严重



首先我们需要明确一个前提：

在这样一个分布式、高并发的系统里、追求**强一致性**（即任何时刻、所有缓存和数据库的数据都完全一样）是不现实的、它会极大地牺牲系统性能和可用性

因此我们的设计目标是实现**最终一致性（Eventual Consistency）、**并尽可能缩短数据不一致的窗口期



为了达到这个目标、我设计了一套三位一体、层层兜底的保障体系、它由准实时层、增量校对层和全量兜底层构成

确保数据在绝大多数情况下是准实时的、并且最终100%会达成一致





**三重方案**：更新 DB 时发消息到 NQ 异步更新 Redis、监听 DB 的 binlog 进行增量对账修复、以天为维度定时全量扫描数据与 Redis 对比修复。



**第一层：准实时层 —— MQ异步通知**



- 这是什么？
- 这是保证数据更新速度最快的一层。它的核心思想是主动通知
- **工作流程是怎样的？**

  - 当运营同学在管理后台**更新一个黑名单**时（例如拉黑一个恶意抢注域名的用户）、我们的业务代码会执行两个操作：
  
    - 第一步：**更新数据库**
    - 第二步：向一个**消息队列（MQ、比如腾讯内部的Ckafka/TDMQ）** 发送一条变更消息
    - 这条消息内容很简单、比如 `{"key": "blacklist:user_id:abcde", "action": "ADD"}`。
  - 我们有一个独立的**缓存同步服务、**它会订阅这个MQ主题
  - 当它收到变更消息后、会立即去更新**Redis缓存**
- **为什么这么设计？**

  - **性能与解耦**：通过MQ实现了**异步解耦、**API接口在更新完数据库后就可以立刻返回成功、无需等待缓存更新完成、保证了用户操作的低延迟
  - **可靠性**：MQ天生具备**消息持久化**和**失败重试**机制、即使缓存同步服务短暂宕机、消息也会被保留在队列中、等服务恢复后继续处理、保证了更新操作最终一定会被送达
- 它的局限性？

  - 虽然速度很快、但依然存在极小概率的风险
  - 比如代码bug导致发送MQ失败、或者MQ消息丢失
  - 所以我们需要第二层保障。

- 这是什么？
- 这是保证数据更新最全面、最准确的一层
- **工作流程是怎样的？**

  - 我们知道、MySQL的所有数据变更都会被记录在一个叫做**二进制日志（Binlog）的文件中。这可以说是数据库所有变更的唯一事实源头**
  - 我们部署了一套基于**Canal**（阿里巴巴的开源组件）的**Binlog订阅服务**。这个服务会伪装成一个MySQL的从库、实时地拉取并解析Binlog。
  - 每当它解析出一条数据变更（比如 `UPDATE user_blacklist SET status=1 WHERE user_id=abcde`）、它就会将这个变更事件推送出来
  - 我们的**对账系统**会消费这个事件、并与Redis、Kconf中的数据进行比对
  - 如果发现数据不一致（比如MQ那层漏掉了更新）、它就会**强制用数据库的最新数据去覆盖缓存、**完成修复
- **为什么这么设计？**

  - **100%全面**：无论数据变更是通过API、后台脚本还是DBA手动修改产生的、只要动了数据库、就一定会被Binlog记录下来、我们就能捕获到。这弥补了第一层可能存在的通知遗漏问题。
  - **对业务代码无侵入**：整个监听和对账过程、对原有的域名业务API代码是完全透明的、没有任何侵入
- 它的局限性？

  - 如果Binlog订阅服务本身长时间故障、还是会造成数据不一致的累积
  - 因此我们需要最后一道防线

**第三层：全量兜底层 —— 定时任务全量校对**



- 这是什么？
- 这是我们的终极保险、是整个一致性体系的最后一道防线、它的核心思想是定期审计
- **工作流程是怎样的？**

  1. 我们有一个**定时任务**（比如每天凌晨3点的业务低峰期）、它会去**全量扫描**数据库中的数据表。
  2. 它会把数据库中的每一条记录、都和Redis、Kconf中对应的缓存数据做一次比对。
  3. 一旦发现不一致、就立即进行修复。
  4. 同时它还会产出一份**对账报告**。如果报告中显示差异数量过多、就会触发**监控告警、**通知我们去排查是不是前两层同步机制出了问题
- **为什么这么设计？**

  - **绝对可靠**：无论前两层因为什么疑难杂症失效、这一层都能发现并修复所有问题、保证了数据在24小时周期内的最终一致性。它让整个系统有**自我治愈**的能力。





**面试官：(确认)你订阅数据变更时、数据在产品侧是走到了Kafka（MQ）里、Kafka再把数据放到Redis、是吧？**

我们的**L2（Redis）缓存**是主动推送更新的

当运营在后台拉黑一个IP时、这个变更会（1）写入数据库、同时（2）产品侧会发一条消息到Kafka（或通过Binlog被捕获）

我们的一个后端同步服务会订阅这个消息、然后**主动去更新Redis**

这保证了Redis这个的数据始终是（或无限趋近于）和DB一致的。”

**面试官：（追问）那你本地的cache（L1）是怎么更新的？所有节点都有本地内存、怎么更新到所有节点上去？**



是我们这个架构的精髓所在、我们的**L1（本地缓存）的更新策略和L2完全相反、**它**不是主动推送、而是被动过期**

我们**绝对不会**尝试去‘主动’把一个更新推送到全网几百上千台服务器的本地内存里、原因就是您指出的问题：

1. **状态不可靠**：我们无法保证每一台机器都收到了这条推送、如果一台机器网络抖动丢了消息、它的本地缓存就**永久是脏数据**了。
2. **缓存风暴**：一条数据变更、引发上千台服务器同时响应、这本身就是一场性能灾难。

所以、我们的本地缓存更新逻辑是：**我们从不推、我们只等它拉**

这也就是我们设置**5秒短过期**的真正意义：

1. 每一台服务器的本地缓存都是**独立**的。服务器A不需要知道服务器B的存在。
2. 我们给所有节点的本地缓存都设置了一个统一的、非常短的生命周期、就是**5秒**。
3. **被动拉取（Pull-on-Miss）”**

   - `T=0秒`：运营在后台拉黑了`ip:1.2.3.4`。
   - `T=1秒`：Kafka（MQ）把这个变更**推送**到了**Redis**。
   - `T=1秒 ~ T=5秒`：这是我们的不一致窗口期**。在这4秒内、所有服务器上的本地缓存**依然是旧的“白名单”数据（这是我们为了性能主动做的权衡）。
   - `T=5秒`：**全网所有服务器上、**关于`ip:1.2.3.4`的本地缓存、**不约而同地到期失效了**。
   - `T=5.001秒`：下一个查询`ip:1.2.3.4`的请求、**无论打到哪台服务器（A、B或C）、**它都会发现**本地缓存（L1）未命中**。
   - `T=5.002秒`：这台服务器会穿透L1、去L2（Redis）拉取数据。此时、它**必定会拉取到那个在T=1秒时就已经更新的黑名单新数据**
   - `T=5.003秒`：这台服务器把这个黑名单新数据写回**自己的**本地缓存、并设置一个**新的5秒**倒计时





# 如何保证一致性面试回答



**三重方案**：更新 DB 时发消息到 NQ 异步更新 Redis、监听 DB 的 `binlog` 进行增量对账修复、以天为维度定时全量扫描数据与 Redis 对比修复。



**第一、通过MQ消息队列实现准实时同步**

在核心业务流程中、当运营人员通过后台更新黑名单状态时、我们会采用写DB后立即发送MQ的异步化方案。也就是说、在更新完数据库之后、我们会立刻向消息队列发送一条变更通知、我们有一个独立的**缓存同步服务、**它会订阅这个MQ主题、当它收到变更消息后、会立即去更新**Redis缓存。这是我们保证数据一致性的第一层**



这样做的最大好处是、**主业务流程和缓存更新完全解耦、**保证了API接口的低延迟和高吞吐量。同时我们利用MQ本身具备的**持久化和失败重试**机制、确保了缓存更新的通知能够可靠送达



**第二、通过监听数据库Binlog进行增量校对**

为了防止第一层出现代码Bug或消息丢失等极端情况、我们部署了一套独立的对账系统。它的核心原理是**订阅并解析数据库的Binlog日志**——会记录所有的数据变更。一旦监听到数据变更、它会立刻主动与Redis中的数据进行比对。如果发现数据不一致、它会**强制以数据库为准进行修复**

这一层确保了任何来源的数据库变更、这是我们保证数据准确性的第二层





**第三、通过每日全量任务作为最终兜底**

我们有一个定时任务、以天为维度定时全量扫描数据与 Redis 对比修复。会在每天凌晨的业务低峰期、**扫描前一天发生变更的所有数据、**进行一次**全量的DB-Redis数据比对**



这个过程不仅能修复前两层可能遗漏的任何细微差错

**如果修复任务连续失败并达到我们设定的阈值、就会**触发高级别告警、通知人工介入、这套机制确保了系统具备自我审计和异常发现的能力、保证了在业务方真正使用时、数据是100%可靠的









我们的定时任务**不是**一个简单的`SELECT *`、而是通过一种滚动分片的方式来执行的。

这是我们的具体做法和校验逻辑：



# **面试官：你们这个全量校对的定时任务具体是怎么做的？怎么校验的？**



# 凌晨的定时校验任务一般放在什么时候执行？是否有专门的数据质量监控机制？

好的。这个全量校对任务是我们一致性保障的最后一道防线、**它的核心设计目标是**绝对准确、对线上无感、

我们的做法并不是在凌晨3点跑一个巨大的`SELECT *`、因为对于我们腾讯云这种亿万级别的域名数据来说、这会是灾难性的



我们采用的是一种**基于主键`ID`的滚动分片校验**



**第一步：如何做 —— 滚动分片扫描**



1. 我们在业务低峰期（比如凌晨3点）启动这个定时任务。这个任务会从数据库中读取一个游标（Cursor）**、这个游标记录了**上次校验结束的主键ID、比如 `last_checked_id = 15,000,000`。”
2. 任务开始后、它会以这个ID为起点、**分批次**拉取数据。比如一次拉取**1000条、**它的SQL类似于：`SELECT id, key_name, data_hash FROM blacklist WHERE id > 15000000 ORDER BY id ASC LIMIT 1000`
3. 它会校验这1000条数据、完成后、**更新游标**为这批数据的最大ID `last_checked_id = 15001000`、然后拉取下一批
4. 这个任务会一直这样滚动下去、直到它扫描完当天的所有数据。我们还会设置**速率限制、**比如每秒钟只允许执行几次这样的查询、确保它对数据库的CPU和IOPS（磁盘读写）占用始终保持在一个非常低的水平、对线上业务完全无感



**第二步：如何校验 —— 高效的哈希比对**



在拿到这一批1000条数据库记录后、**我们不会去比较完整的JSON数据、因为那太慢了**

我们的做法是、在数据库表里就冗余了一个关键字段：**`data_hash`**。这个哈希值（比如MD5）是在数据写入或更新时、根据它的完整内容计算出来的。所以、我们的校验逻辑非常高效

1. **批量获取缓存**：我们拿着这1000条记录的`key_name`、使用Redis的`MGET`（批量获取）命令、一次性从Redis中取出所有对应的缓存数据
2. **逐条比对**：

   - **情况一：Redis中根本不存在这个Key**。
   
     - **结论**：数据不一致（DB有、Redis没有）
     - **操作**：触发**修复**。
   - **情况二：Redis中存在这个Key**
   
     - **结论**：我们需要比对内容。
     - **操作**：我们在内存中**实时计算**这个Redis Value的哈希值、然后和从DB中带过来的`data_hash`字段进行比对。
     
       - **哈希一致**：数据一致、跳过
       - **哈希不一致**：数据不一致（DB和Redis内容不同）。触发**修复**。



**第三步：如何修复与告警 —— 闭环处理**



这一步就是你刚才提到的‘修复、重试和告警的逻辑、我们称之为审计闭环

1. **触发修复**：一旦发现不一致（无论是Key丢失还是哈希不匹配）、我们会向一个修复队列（也是一个MQ）里丢一条消息、内容就是请以DB为准、同步`key_name`这条数据
2. **失败重试**：专门的修复服务会消费这个消息、去更新Redis。如果更新失败（比如Redis瞬断、、它会**自动重试3次**。
3. **触发告警**：如果重试3次后**依然失败、**系统会停止重试、并将这条失败记录存入死信队列、同时立即触发**P0级（最高级别）监控告警、**通知SRE和我们开发人员立即人工介入、因为这通常意味着系统出了大问题（比如Redis集群彻底不可用）
4. **生成审计报告**：当整个扫描任务完成后、它会生成一份审计报告、比如：`【全量对账报告】总扫描数：1.3亿、发现不一致：15条、自动修复成功：15条`。这份报告会发到我们的工作群、如果发现的不一致数量**超过了一个阈值**（比如100条）、会自动告警、因为这说明我们的**第一层（MQ）或第二层（Binlog）同步机制可能已经失效了**

通过这套滚动扫描 + 哈希校验 + 自动修复 + 阈值告警的闭环流程

我们就实现了一个既能100%覆盖全量又对系统几乎0压力的健壮的兜底方案

















# 你提到更新DB后发送MQ、那我要确认：如果更新DB成功了、但发送MQ时因为网络波动或者MQ集群临时故障、导致消息没发出去、这种场景你们是怎么处理的？是让业务接口直接返回失败、还是有重试机制？如果重试、重试几次？重试失败后有没有兜底的补偿动作？



1. 先解决 消息不能丢：在代码里、把 发送 MQ和 更新 DB 用本地事务或者事务消息绑定 —— 如果是普通 MQ、至少要加**本地重试机制、**比如最多重试 3 次、每次间隔 1 秒、重试失败就把消息暂存到 失败消息表、避免直接丢消息。
2. 再解决 失败后怎么补：失败消息表的数据不能一直放着、要加一个**补偿定时任务**（比如每 5 分钟扫一次）、把没发出去的消息重新推送到 MQ、直到成功、同时要加监控、一旦失败消息表数据量超过阈值就告警、避免堆积。



如果更新DB成功但发送MQ失败、我会采取以下策略。



首先在代码层面、我会设置一个本地重试机制。当检测到发送MQ失败后、系统会立即进行第一次重试、并且在每次重试之间设置一个合理的时间间隔、比如从500毫秒开始、每次重试间隔翻倍、最多重试3次。这样既不会因为过于频繁的重试给MQ服务器造成压力、又能在一定程度上解决临时性的故障问题。



要是经过3次重试后依然失败、我会将这条失败的消息记录到一个专门的失败消息表中

这个表会详细记录消息的内容、发送失败的时间、失败原因等关键信息、以便后续的排查和处理。



针对这个失败消息表、我会设计一个补偿定时任务。该任务会定期（比如每分钟）扫描失败消息表、将其中的失败消息再次尝试发送到MQ。在发送前、会再次检查消息对应的业务数据（如DB中该域名黑白名单的状态是否还符合发送条件）、确认无误后进行发送。若再次发送失败、会更新失败消息表中的失败次数和最新失败时间。



为了防止失败消息表的数据无限膨胀、我会设置一个数据清理策略。

对于那些经过多次重试（比如5次）仍然失败、并且经过人工评估后确认无需再重试的消息、可以进行归档处理、同时保留必要的日志记录、以便后续追溯



此外我还会在系统中添加相应的监控。一旦失败消息表中的消息积压数量超过某个预设的阈值（如100条）、或者某个消息的重试次数达到一定极限（如5次）、系统会立即触发告警、通知相关的开发和运维人员、以便他们及时介入、排查并解决可能存在的深层次问题、比如MQ服务器的配置问题、网络故障等



这样的设计能够最大程度地保证在更新DB成功的情况下、MQ消息也能可靠地发送、确保数据一致性在这一关键环节的稳定性

















# **域名黑白名单系统的缓存策略是什么样的？**



针对**域名查询、秒杀抢注**这类高并发、低延迟的业务场景

我设计的核心策略是多级缓存’架构、也叫做L1 + L2缓存模式、它的目标是在离用户请求最近的地方返回结果、最大限度地保护后端数据库

- **L1 级是SDK本地缓存：** 这一层是性能最高的、它直接在**应用服务的JVM内存中**（我们使用Guava Cache实现）。它的主要目标是拦截**瞬时流量洪峰**和解决**热点Key问题**。比如在域名秒杀时、`promo:``1yuan.com`这个Key会成为热点、本地缓存可以将其压力分散到上千台服务器上、避免了对Redis的单点冲击
- **L2 级是Redis分布式缓存：** 这一层是我们的共享缓存。当本地缓存未命中时、请求会查询`Redis`。它为整个集群提供了统一的缓存视图、并拦截了99%以上对数据库的访问压力
- **最后是数据库：** 作为数据的最终来源。只有当本地缓存和Redis都未命中时、才会查询数据库



通过这个策略、我们最终实现了**近万QPS**的峰值支撑、并且核心查询场景的**本地缓存命中率达到了97%以上**









# **缓存的更新策略是怎样的？比如一条数据更新后、如何更新二级缓存（本地缓存 + Redis）？**



这是一个非常好的问题、它触及了多级缓存一致性的核心。我们对L1和L2缓存采用了**截然不同的更新策略**

- **对于L2（Redis）的更新：我们采用MQ异步通知的方式**

  - 当运营人员通过管理后台更新一条黑名单时、业务API在**写入数据库**后、会立即向一个**MQ主题**发送一条变更消息
  - 我们有一个独立的缓存同步服务、会订阅这个MQ主题。一旦收到消息、它会**立即去更新或失效Redis中的对应数据**。这样做的好处是主业务流程与缓存更新解耦、保证了API的低延迟
- **对于L1（本地缓存）的更新：我们采用被动过期**

  - 我们**不会主动去通知**上千台服务器更新它们的本地缓存、因为这会引发缓存消息风非常复杂且不可靠
  - 相反、我们在设计时就给本地缓存设置了一个**极短的过期时间——5秒**。这意味着、即使数据在Redis中更新了、本地缓存最多也只会存在**5秒钟的脏数据、**5秒后它会自动失效、下一次请求会穿透到`Redis`、拉取到最新的数据并重新缓存在本地









# **订阅 MQ 消息更新 Redis 后、Redis 缓存是永不过期还是会定期过期？**

我们在设计 Redis 缓存策略时、没有采用单一过期方案、而是根据数据访问特征做了区分。

- 对**普通数据（99%）、**我们采用 **定期过期（24小时+随机值）**。  
 这样做有三点考虑：  
 一是作为**兜底机制、**防止 MQ 或 Binlog 更新链路出现异常导致永久脏数据  
 二是**节省内存、**避免冷数据长期占用  
 三是**随机TTL**可以防止大量 Key 同时失效引发缓存雪崩
- 对**极度热门且稳定的数据（<1%）、**比如公司核心域名、我们采用 **永不过期策略**。  
 这类数据访问量极高、更新频率极低、而且更新路径完全可控（通过工单或 MQ）、我们信任主动更新机制、用永不过期换取极致性能和稳定性。

所以总结来说、我们的策略是双轨制

 普通数据优先保证可靠性、核心数据优先保证性能。

 这种设计既防止了脏数据问题、也能在高并发场景下保持系统的高可用与高性能。







在我们的**域名风控系统**中、我们并不是采用单一的策略、而是根据数据的访问频次**和**稳定性、**设计了一套**差异化的缓存过期体系

我们的缓存数据、大体可以分为两类：

**第一类：绝大多数的、普通的数据（占比99%以上）**

- **这是什么？** 比如：一个普通用户的域名黑名单、一个新注册的`my-cool-blog.com`域名的信息、一个普通的API调用者的IP黑名单。
- **采取什么策略？** **采用定期过期策略（例如24小时+随机值）**
- **为什么？**

  - **作为兜底（Fail-safe）**：这就是我之前提到的、我们必须假设MQ和Binlog有**极端情况**下会失效。如果一条黑名单更新失败了、并且这个Key永不过期、那它就成了**永久的脏数据、**这是风控系统的大忌
  - **节约内存**：这些数据访问量并不高、没必要永久占用宝贵的Redis内存。24小时过期可以让系统自动清理掉这些冷数据。
  - **所以对于这99%的数据、我们选择可靠性优先、宁愿让它过期后回源DB、也绝不容忍它成为永久的脏数据**

**第二类：极少数的、极度热门且稳定的数据（占比 < 1%）**

- **这是什么？** 这就是你提到的热门域名。比如 `tencent.com`、`qq.com`、`weixin.com` 这些我们自己核心资产的域名记录。或者一些合作商的域名
- **采取什么策略？** **采用永不过期策略**
- **为什么？**

  - **极致的性能要求**：这些Key每秒钟的访问量可能是天文数字。对于它们、**任何一次缓存回源都是不可接受的**。哪怕只有一秒钟的缓存失效、都可能导致海量的请求穿透到数据库、引发雪崩
  - **极高的数据稳定性**：`tencent.com` 的核心解析记录、可能几年都不会变动一次
  - **100%的更新可控性**：这种核心资产的变更、一定是**有计划、有流程的**（比如通过工单系统）。我们100%确信这种变更**一定会触发MQ和Binlog、**我们的主动更新机制是绝对可靠的。
  - **所以对于这1%的核心数据、我们选择性、优先。我们信任我们的主动更新机制、用永不过期来换取它绝对的稳定和100%的缓存命中率**

**总结一下：**

因此、我们的系统是**两种策略并存**的：

对**普通数据、**我们使用定期过期作为兜底、保证**可靠性**

对**核心热门数据、**我们使用永不过期并依赖主动更新、保证**极致的性能**













# **本地缓存的刷新机制是什么样的？是否通过过期方式刷新？**



它的核心刷新机制就是基于时间的被动过期

具体来说、我们使用的是**Guava Cache、**并配置了`expireAfterWrite=5s`。它的工作流是：”

1. 一个请求进来、查询本地缓存
2. 如果命中、且数据未满5秒、直接返
3. 如果未命中、或者数据已满5缓存、会认为它失效
4. 请求会**穿透**到下一级（Redis）、拿到新数据后、重新写入本地缓存、并**重置一个5秒的计时器**



- **对于L1（本地缓存）的更新：我们采用被动过期**

  - 因为有很多台服务器有自己的本地缓存
  - 我们**不会主动去通知**上千台服务器更新它们的本地缓存、这会非常的复杂
  - 所以我们不更新本地缓存、采用的是等待他自动过期。
  - 我们在设计时就给本地缓存设置了一个**极短的过期时间——5秒**。这意味着、即使数据在Redis中更新了、本地缓存最多也只会存在**5秒钟的脏数据、**5秒后它会自动失效、下一次请求会穿透到Redis、因为 MQ 已经更新过 Redis了、他会拉取Redis 的最新的数据、然后重新写回在本地缓存中









# **本地缓存通过过期方式刷新、是否会存在短时间的数据不一致问题？**



**是的、一定会存在、这是我们设计时的一个主动权衡（Conscious Trade-off）**

在我们的架构里、数据不一致的窗口期是**可控的、**最长就是**本地缓存的过期时间、即5秒**

**举个例子**：在第1秒、运营将一个恶意IP拉黑、MQ和Binlog在第2秒更新了Redis。但在某台服务器上、这个IP的白名单状态在第0秒刚被缓存在本地、它需要等到第5秒才会过期。那么在这3秒的窗口期内、这台服务器会错放这个恶意IP的请求 

**但这个权衡是完全值得的**：

对于我们的域名风控业务来说

**5秒的策略延迟是完全可以接受的**

我们用这5秒的延迟、换来的是**系统扛住了97%的瞬时洪峰流量**、避免了后端Redis和DB被瞬间打垮

如果我们为了追求这5秒的强一致性、而去采用分布式锁或实时通知、那整个系统的性能会下降几个数量级、也就失去了这个架构的意义

# **之前提到用 MQ 的方式会丢消息、一般是什么情况下会丢消息？**



它可能发生在三个阶段：**生产者、Broker（MQ服务器）和消费者**

1. **生产者 -> Broker 阶段丢失**

   - **情况**：我们的业务API（生产者）发送消息、但网络抖动或者MQ服务器正好重启、消息没发出去。如果代码写得不规范、没有处理好异常或回调、这条消息就凭空消失了。
   - **对策**：我们会配置**可靠的发送机制、**比如**同步发送并检查ACK、**或者**异步发送但必须有失败重试的回调**。
2. **“Broker 存储阶段丢**

   - **情况**：这是最危险的。Broker收到了消息、把它放在内存里、就先给生产者返回了OK、但它还没来得及把消息**持久化到磁盘、**Broker自己宕机了。消息就丢了。
   - **对策**：我们会配置高可用的MQ集群、**强制要求数据刷盘（Persist to Disk）**、并且至少要同步到一个副本（Replica）之后、才允许返回ACK
3. **Broker -> 消费者 阶段丢失（最常见）**

   - **情况**：我们的缓存同步服务（消费者）拉到了消息、但它**开启了自动ACK、**它刚拿到消息、还没来得及更新Redis、自己就异常崩溃了。MQ服务器以为它处理成功了（因为自动ACK了）、就把消息删了、导致消息丢失。
   - **对策**：我们严格采用手动ACK（Manual Acknowledgment）**模式。我们的消费者必须在**成功更新完Redis之后、才手动地告诉MQ：我处理完了、你可以删这条消息了、如果它在更新Redis时崩溃、MQ没收到ACK、会把这条消息重新投递给另一个健康的消费者、确保消息**至少被消费一次**

通过在这三个阶段的配置和保障、我们就把丢消息的概率降到了最低

即使真的发生了、我们还有第二层（Binlog）和第三层（全量对账）来兜底



你这个问题问到点子上了！**你猜的完全正确、**但这只说对了一半。

引入Binlog并不仅仅是对MQ丢失消息的Plan B、它和MQ解决的是两个不同层面、但又互为补充的问题。

我们来深入聊一下这个设计思路。









# **面试官：我看到你既用了MQ、又用了Binlog、这会不会有点重复？为什么有了MQ还要引入Binlog呢？**



你这个问题非常专业

在系统设计的初期、我们的第一版方案确实**只有MQ**

因为它的逻辑最简单：**业务API更新DB -> 顺手发个MQ -> 消费MQ更新缓存**



这个方案在绝大多数情况下运行良好、但我们在后续的复盘和压力测试中、发现了两个它**无法解决的致命缺陷、**这促使我们必须引入Binlog作为第二层保障



**缺陷一：MQ本身无法保证100%不丢消息**



第一点就像你提到的、虽然我们采用了各种高可用配置（如手动ACK、生产者重试）、但在极端情况下MQ依然存在丢失消息的可能。比如：

- 生产者（我们的业务API）在发送消息时、因为代码Bug或网络瞬断、**发送失败了、它又没有正确地重试或告警**
- 或者在消费者端、它拉取了消息、但在处理完成、**手动ACK之前就宕机了、**而这条消息因为某些原因（比如MQ集群的Bug）没有被正确地重新投递

对于一个普通的业务系统、丢几条消息可能问题不大

但我们这是**域名风控系统、一条消息的丢失、就意味着一个恶意IP可能被永久错放、**这是绝对不能接受的





**缺陷二：存在绕过MQ的数据变更**



这一点是MQ方案的**根本性盲区**。MQ同步机制有一个前提：**你必须通过我的API来写数据、我才能发MQ通知你**

但在实际的生产环境中、修改数据库的途径太多了：

1. **DBA紧急运维**：比如、某个大客户（比如一个游戏公司）的域名被误拉黑、导致全网服务中断。SRE或DBA会立刻**跳过所有业务API、直接连接数据库执行`UPDATE`命令**来紧急解封。这个操作**根本不会触发MQ**
2. **离线批量任务**：我们每天凌晨会从安全部门同步一份最新的高危域名库、这个批处理脚本为了效率、可能会**直接批量`INSERT`到数据库**。这个操作也**不会触发MQ**
3. **其他遗留系统**：可能还有一些老的、没有接入MQ的后台系统、它们也会修改这张表

在这些情况下、MQ是完全不知情的。如果我们只依赖MQ、数据库和缓存之间的数据就会**永久不一致**

好的。要回答这个问题、我先得描述一下我们这个域名秒杀的具体场景、因为它直接决定了我们的技术选型

（回答 Q21:29 和 Q22:28：秒杀是什么？并发量高吗？）



一个典型的场景就是我们运营部门推出的域名秒杀活动

比如、我们在晚上8点整、限量1000个1元域名、用户会盯着倒计时来抢购

这个场景的并发特点是：**请求在时间上高度集中**。在8点整的**第一秒、**可能会有**数万个请求**涌入、竞争这1000个名额。所以、它的并发量是非常高的、而且是集中在库存扣减**和**风控校这两个核心点上

# **面试官：那在这种高并发下、你如何避免黑白名单错判？（Q20:40）毕竟你的缓存同步是异步的**



这是一个最关键的问题。您说得非常对、我们系统的常态是MQ + Binlog的异步同步、并且为了性能、我们还有一个**5秒过期的本地缓存**

如果在平时、5秒的数据延迟是完全可以接受的。**但在秒杀场景下、5秒的延迟是致命的**

一个羊毛党脚本（黄牛）可能在第1秒被我们运营拉黑、但在第2秒、他利用这5秒的本地缓存窗口期、成功抢到了域名。

因此、我们的‘防错策略’是：**针对秒杀这类高优先级的写事务、我们动态调整了缓存策略、牺牲了部分性能来换取强一致性**

具体做法是：

1. **绕过本地缓存（L1 Cache）**

   - 当一个请求进入的是秒杀交易这个接口时、我们植入的**SDK会智能识别**出这是一个高风险、高一致性要求的操作。
   - 它会**强制绕过5秒的本地缓存、**根本不会去读
2. **强制直连Redis（L2 Cache）**：

   - SDK会**强制这个请求直接穿透到Redis、**去读取Redis中那个（由MQ和Binlog维护的）最新的黑名单数据
3. **主动的策略权衡**：

   - 我们非常清楚、这样做会**显著增加Redis的QPS压力、**因为我们放弃了本地缓存97%的命中率
   - 但这是一个**有意识的、主动的架构权衡**。我们认为、在秒杀场景下、**防止错放一个黄牛**所带来的业务价值、远大于牺牲一点性能的代价。我们绝不能容忍因为数据异步性、导致风控策略在关键时刻失效















# **面试官：1000个人同时抢、你们如何保证整个秒杀抢购过程的数据不错乱？（Q23:03）**



Redis 分布式锁+ Lua 脚本实现的







我们主要解决两个并发一致性问题：

1. 库存超卖
2. 用户重复下单

对应采用**分布式锁 + Lua 脚本**组合方式。

1. 用户维度分布式锁：防止重复下单

基于 `user_id` 做 Redis 分布式锁。  
 命令：  
`SET lock:seckill:userId requestId NX PX 3000`

效果：

- NX：只有第一个请求能获得锁
- PX：自动超时释放、避免死锁  
 同一用户多个请求同时发送、只有一个能进入流程、有效阻断**重复下单**

1. Lua脚本原子化扣库存：防止超卖

核心抢购逻辑全部写入 Lua、通过 Redis 单线程执行原子性保证：

Lua脚本内部操作顺序：

1. 校验是否已购（SISMEMBER）
2. 校验库存（GET or DECR前判断）
3. 扣减库存（DECR）
4. 记录已购用户（SADD）

整个逻辑一次执行、不会被其他请求打断、彻底避免**库存超卖**











# 缓存里存的是什么东西



缓存的数据主要分为两类：

**第一类：风控名单实体（用于反刷、防攻击）**



这是我们系统的主要数据。它的特点是**Key轻量、Value简单**。

- **场景**：用于判断某个请求源是否合法、比如反API攻击、拦截恶意IP。
- **Key**：就是这个请求源的唯一标识。

  - 例如：`"blacklist:ip:1.2.3.4"`
  - 或者：`"blacklist:user:abcde123"`
- **Value**：就是一个**布尔值、**或者一个包含简单信息的JSON

  - 例如：`"true"`
  - 或者：`{"level": "P1", "reason": "api_abuse", "expire_at": 1678888888}`



**第二类：高价值资产状态（用于秒杀、拍卖）**



这就是你提到的热Key**数据。它的特点是**Key固定、Value会被高频读写

- **场景**：用于域名秒杀或溢价域名拍卖、比如 `8888.com` 的抢购
- **Key**：就是这个特定资产的唯一标识。

  - 例如：`"promo:domain:8888.com:stock"` (这个Key用于存储 `8888.com` 这个秒杀活动的**库存**）
  - 或者：`"auction:domain:8888.com:info"` (这个Key用于存储 `8888.com` 的**拍卖状态、**如当前价格、剩余时间）
- **Value**：是这个资产的**状态数据**

  - 例如：`"9"` (表示库存还剩9个)
  - 或者：`{"current_price": 50000, "end_time": 1678889999}`
- 第一类数据（风控名单）、是为了做出**是否放行**的决策。
- 第二类数据（高价值资产）、是为了做出**是否售罄**或**是否中标**的决策。



# 那你这个有这么多机器、那你是要将 Redis 的数据写到那么多个机器的本地缓存中吗？那比如说一个热门域名 你怎么在一开始就放到缓存中呢？还是说用户请求过来打到机器、然后机器发现本地缓存没有然后去 Redis 里去查。然后后续打到这个机器的请求都可以从本地缓存中去拿了



我们不会主动的去写本地缓存、

假设我们有1000台服务器。当Redis里的一个`key`更新了、如果我们去通知这1000台服务器。这本身就很复杂、我们没有办法保证那么多台机器的缓存都更新成功

如果这些服务器在收到通知后、都**同时**去Redis拉取新数据、那这个`key`会瞬间成为一个**超级热点、**反而把Redis打垮了

所以我们采用的是被动拉取的、每一台机器的本地缓存都是独立的、设置过期时间 5s。当一个请求打到服务器 A 的时候、A 只关心自己本地缓存、如果缓存没过期就返回信息、如果未命中就会穿透到 Redis、然后再拉取 Redis 的数据到本地化内存中。



以及针对热 key 的问题、对于一个**已知的、即将会变热**的Key、比如我们要在晚上8点整开始秒杀 `8888.com`

我们就会用缓存预热去解决冷启动的问题、我们针对流量的突发性、会在拍卖开始前、主动从数据库将一些热门域名的信息查询出来写到 Redis 缓存中、而本地缓存就是空我们不设置。然后秒杀开始的时候、第一波请求会穿透到 Redis、但是我们已经预热够了、Redis 在内存中运行很快、可以扛住第一波请求。然后再将 Redis 返回的数据各自写到各自机器的本地缓存。之后的请求都打到本地缓存中





# 假如说这个存储的是黑名单 IP、那你在刷 IP 的时候有 5s 的过期时间、第一次请求的时候会访问 Redis 更新到本地缓存、那剩下的 4s 内就可以命中本地缓存对吧？假如第二波请求又来了呢？？还有就是这个 IP 存到 Redis 是永不过期吗？



第一个请求打到服务器 A、本地缓存未命中就会穿透到Redis 中 、然后 Redis 写回本地缓存并设置 5s 过期时间、再次请求的时候已经拉黑了。从 `T=0.011 秒` 到 `T=5.0 秒` 这段时间、**任何**对`ip:1.2.3.4`的请求、**只要它打到的是服务器A、**都会**100%命中本地缓存（L1）、**在1毫秒内直接返回、根本不需要再访问Redis



第二波的话会重复以上操作无限循环



而且这个 key 不是永不过期的

- 在我们的架构里、只有**极少数（<1%）**、**极度热门**、且**数据状态极其稳定**的Key、我们才会设置为永不过期
- 比如你提到的`8888.com`这种**高价值域名资产、**或者`tencent.com`的解析记录



黑名单 IP 属于一个风控管理、如果它再刷我们的接口、但是状态不稳定、我们会给他设置一个较长的过期时间、可能 24小时等等。因为他肯定不会一直访问、也有可能会切换 IP。





# 那黑名单呢？假设是这个习近平.com 你觉得这个在 Redis 中需不需要永不过期

<cite doc-id="ZDS9wNb4UiEiqUknAzwcF8SRn0g" file-type="wiki" title="域名黑白名单面试题汇总" type="doc"></cite>



**面试官：那黑名单呢？假设是这个`习近平.com`、你觉得这个在 Redis 中需不需要永不过期？**

**是的对于 `习近平.com` 这种Key、它在Redis中必须设置为永不过期**

就引出了我们缓存策略的第三层、

我来解释一下为什么它和普通的`ip:1.2.3.4`黑名单**完全不同**：

1. **风险模型的不同：**

- **`ip:1.2.3.4` (动态风控数据):**

  - **特点:** 状态是**动态的**（今天拉黑、明天可能就解封了）。
  - **最高风险:** **假设是永久脏数据、**如果我们MQ/Binlog的解封消息丢了、而它在Redis里永不过期、那这个用户就**永远被错杀了**。
  - **策略:** **必须设置24小时兜底过期**。我们用系统最终会自动纠错来保证**可靠性**
- **`习近平.com` (静态策略数据):**

  - **特点:** 状态是**永久的、静态的**（它永远、100%是黑名单、绝无可能被解封）
  - **最高风险:** **缓存失效 (Cache Miss)**。如果它在Redis里过期了（哪怕只有1秒）、万一那一瞬间DB抖动或MQ卡住、导致缓存回源失败、就可能错放**了一个请求、让这个域名被注册成功。这个后果是**灾难性的、不可承受的
  - **策略:** **必须设置为永不过期**。我们100%信任我们的主动更新机制（MQ/Binlog）、用它来换取**100%的缓存命中率**和**100%的策略执行**。

1. **和“热Key”的殊途同归：**

所以、`习近平.com` 这种合规数据、和我们之前讨论的 `8888.com` 或 `tencent.com` 这种高价值资产、在架构上**属于同一类**

# 那假设我们秒杀一个一元域名、这个具有流量的突发性他是一个热 key、那 Redis 存储的 key 是这个域名信息、value 是这个什么？你之前说是库存、那你设置的过期时间5s、在这 5s 的秒杀活动中会不会有数据更新来不及、比如说库存状态来不及更新、导致超卖等情况、或者说价格拍卖更新不及时





**为什么5秒的秒杀活动中不会导致超卖？**

库存状态来不及更新、导致超卖、在一种落后的架构下（`GET-Check-SET`：先读库存、再判断、后减库存）是一定会发生的

**但我们的系统根本不使用这种方式**

我们100%杜绝超卖的手段、是**Redis的Lua脚本**。

**请看这个流程：**

- `T=0秒`：秒杀开始、1000个请求（代表1000个不同用户）同时涌入、要抢这1000个库存。
- 这些请求**全部**（如我们之前所说、秒杀事务会**绕过L1本地缓存**）被发往Redis、执行我们预先写好的一个Lua脚本。
- **Redis是单线程的**。它会把这1000个请求**排成一个队列、**一个一个地执行Lua脚本。

**这个Lua脚本在Redis服务端是原子的、它会一次性做完三件事**

1. **（风控校验）**：检查`user_id`是否在黑名单。
2. **（库存校验）**：`GET promo:stock:1yuan_com`。检查当前库存是否 `> 0`。
3. **（库存扣减）**：如果`> 0`、就执行 `DECR promo:stock:1yuan_com`（将库存减1）。

**结果就是：**

- 第1个请求：执行脚本、库存从`1000`变成`999`。
- 第2个请求：执行脚本、库存从`999`变成`998`。
- ...
- 第1000个请求：执行脚本、库存从`1`变成`0`。
- 第1001个请求：执行脚本、在第2步（库存校验）时发现库存为`0`、脚本立刻退出、返回已售罄



**结论**：由于Lua脚本的原子性和Redis的单线程性、**库存状态的更新是100%实时的、绝对不会来不及的**

这就从根本上杜绝了超卖的可能

## 总体思路（多通道、分级负责）

1. **主动推送（主路径 · 实时）**

   - 数据在 DB 变更时、通过 **MQ / Binlog → 缓存同步服务** 实时写 Redis（对核心数据优先）。这是主更新链路、保证秒级刷新
2. **被动回源（请求触发 · 即时）**

   - 当 Redis key 过期或不存在时、首个到达的请求会触发回源（从 DB / 或调用外部服务）并重建 Redis。常见实现是「lazy load / cache-aside」。
3. **后台预热/刷新（预防与兜底）**

   - 对已知热点做**预热**（活动前主动写 Redis）、对全量一致性问题用**定时全量校验**（你已有的每日扫描）作为最终兜底
4. **监控与自动化修复（安全网）**

   - 告警、死信队列、失败消息重试、异常速率检测、确保任何环节失效能被自动或人工触达并修复。

---

## 如果 Redis 过期了 —— 具体谁来写？（按优先级说明）

### A. 首选：**MQ / Binlog 实时推送**（若变更来源是 DB）

- 当数据在 DB 改变（例如：把某 IP 拉黑或撤销）时、业务会写 DB 并发 MQ、缓存同步服务消费 MQ 后**立即更新 Redis**。
- 对于核心/稳定且访问极高的 Key、我们把它设为 **永不过期**（或极长 TTL）并完全依赖 MQ/主动更新

### B. 请求触发：**`Cache-aside`（懒加载） + 互斥保护**

- 普通 Key 过期后、**首个请求**会触发回源流程：

  - 应用检查到 Redis MISS → 尝试加分布式锁（SET lock:key NX PX ... / SETNX 或 singleflight）防止并发穿透；
  - 获锁者从 DB 读取数据并写回 Redis（设置合适 TTL）、然后释放锁
  - 其他并发请求要么等待、要么返回「过期但可用的旧值（stale）」或降级结果。
- 这样能避免大量并发同时去 DB/RDS 的击穿问题（thundering herd）。

### C. 后台主动刷新：**Keyspace Notifications / Refresh Worker / Pre-warm**

- 使用 Redis 的 **Keyspace Notifications**（`keyevent@*:expired`）或自建的过期扫描（定时 worker scanning）来**监听过期事件**：

  - 一旦某类 Key 过期、后台 Refresh Worker 可异步回源并更新 Redis（适合允许运行短延迟刷新的场景）。
  - 注意：Keyspace Notifications 在 Redis 集群或多实例上要谨慎（可靠性/性能）、常见做法是做为辅助手段并结合 rate-limit/worker pool。
- 对已知将要成为热点的 Key（比如秒杀活动）、预热/主动刷新是在活动前写入 Redis、避免冷启动

## 并发/保护机制（必讲面试必问点）

- **单机/分布式互斥**：`SET lock NX PX / RedLock / singleflight`（服务端实现） 防止并发回源。
- **`Stale-While-Revalidate`**：在刷新的同时可返回略老（但可用）的数据、减少延迟与失败率。
- **降级与限流**：当后端不可用时、返回降级视图或限流保、护核心系统
- **预热 + 灾备**：活动前预热、活动中限流、活动后回收。

## 针对某域名突然变火的风险（热 Key 动态应对）

1. **自动检测**：监控 Redis QPS、`miss rate`、单 Key QPS、一旦超过阈值触发自动流程。
2. **自动升级**：将该 Key 升级为临时永不过期或延长 TTL + 主动刷新、并立即在所有前端节点做预热（或触发 SDK 本地缓存预热）。
3. **加锁保护与熔断**：对该 Key 使用互斥加载、允许少量回源并限流其余请求。
4. **水平扩展/分片**：对极端热点通过流量切分 / 边缘缓存 / CDN 等进一步分流

---

## 失败处理与一致性保障（你已有的三重保障如何协作）

- **主链路（DB → MQ → Redis）**：是最快最常用路径、支持手工重发与失败消息表（dead-letter）。
- **Binlog 监听**：捕获所有 DB 变更（包括 DBA 或批量脚本改动）、作为 MQ 漏消息或绕过 MQ 的补偿通道。
- **定时全量校验（现有的每日滚动分片扫描）**：作为最终兜底与审计、发现差异后放入修复队列并触发告警/人工介入

这三层共同保证「及时性 + 完整性 + 最终一致性」

## 工程实现要点（一句话提示面试官你落地细节）

- 回源流程要做分布式锁与重试（SETNX+过期）；
- 热点 Key 要有监控、自动升级与预热
- 使用随机 TTL 避免雪崩
- 对核心 Key 使用永不过期并由 MQ/ Binlog 驱动更新、同时做每日全量校验作为兜底
- 给失败消息表、死信队列、告警策略、人工排查工具（日志/审计）做完善闭环
